# 向量知识库（Milvus）说明

本文说明 GustoBot 中**基于 Milvus 的菜谱/文档向量知识库**：相关文件职责、端到端数据流，以及核心代码实现要点。

**边界说明**：`gustobot/interfaces/http/knowledge_router.py` 在同一路由下还挂载了 **Neo4j 图谱 QA**（`/graph`、`/graph/qa`）。那是**另一条知识通道**，不是 Milvus 向量库；下文默认「向量知识库」仅指 **Embedding + Milvus + `KnowledgeService`** 这条链路。

**导入操作**：本地 JSON 批量走 `scripts/import_recipes.py`（示例见 [快速开始.md](快速开始.md)）；维基爬虫见 `gustobot/crawler/cli.py`、`gustobot/crawler/wikipedia.py`。多条 RAG 链路对照见 [RAG.md](RAG.md)。

## 0. 文档导读与心智模型（初学者）

### 0.1 你可以把整条链路想成「三个盒子」

1. **正文盒子**：菜谱在业务里是 JSON（`name`、`steps` 等），入库前会被拼成**一段或多段可读中文**（`_format_recipe_document`），再被切成更小的**块**（chunk）。检索时，命中的也是「某一块的文字」，不一定是整道菜的全部信息。
2. **向量盒子**：每一块文字都会经过 **Embedding 模型**变成固定长度的一串浮点数（向量）。语义相近的句子，在向量空间里通常更近。查询时，用户问题也会被编成一条向量，去和库里的向量比「谁更近」。
3. **索引盒子（Milvus）**：向量太多时不能暴力全表比对，需要 **向量索引**（如 IVF、HNSW）。索引有参数（如 `nprobe`、建索引时的 `nlist`），会影响**速度**和**召回质量**——不是「建了库就一定能搜到」，也和数据量、分布有关。

**一句话**：入库 = 文本 → 切块 → 向量化 → 存 Milvus；检索 = 问题向量化 → 在 Milvus 里找近邻 →（可选）重排 → 把文字交给 LLM 组织回答。

### 0.2 和「关键词搜索」的差别

传统数据库 `LIKE '%番茄%'` 要字面一致；向量检索是**语义相似**（「西红柿炒蛋」和「番茄鸡蛋」可能更近）。但若你的数据里根本没有相关菜名/步骤，再强的向量也**检索不到**——RAG 不是魔法，**库里有什么是上限**。

## 1. 端到端数据流（入库与检索）

```text
入库（HTTP）
  客户端 POST /api/v1/knowledge/recipes 或 /recipes/batch
       → knowledge_router（Pydantic 校验、补全 recipe id）
       → KnowledgeService.add_recipe / add_recipes_batch
       → _format_recipe_document 拼成中文正文
       → ingest_text：RecursiveCharacterTextSplitter 切块
       → OpenAICompatibleEmbeddings 批量嵌入
       → VectorStore.add_documents 写入 Milvus

检索（对话主图 KB 分支）
  kb_tools 节点 knowledge_query
       → KnowledgeService.search
       → embed_query + vector_store.search（可 filter_expr）
       → 可选 Reranker.rerank
       → 拼上下文 + LLM 生成回答（可选联网 SearchTool）
```

### 1.1 入库时「一条菜谱」在库里长什么样？

- **逻辑上**：你仍按「一条菜谱」导入（HTTP 里一个 `RecipeModel` / 一个 dict）。  
- **物理上**：Milvus 里存的是 **多块向量行**，主键形如 `recipe_xxx_0`、`recipe_xxx_1`…（`recipe_id` + 块下标）。  
- **原因**：长文本若整段只生成一个向量，容易「语义被冲淡」；切块后，「步骤 3：勾芡」这类局部更容易被问题单独命中。  
- **副作用**：删除时要按 `**recipe_id`** 删（`delete_recipe`），而不是只删某一个 `chunk_id`（除非你自己扩展 API）。

### 1.2 检索时 `score` 是什么？

返回值里的 `score` 来自 Milvus，含义与 `**metric_type**` 有关（如内积 `IP`、余弦 `COSINE`、欧氏 `L2`）。**不同 metric 下分数不可横向比较**，调 `KB_SIMILARITY_THRESHOLD` 时要结合当前 metric 和实际分布试，不要照搬网上的阈值。

### 2.1 配置前缀辨析（避免改错环境变量）

- **重排（`Reranker`）**：`RERANK_ENABLED`、`RERANK_PROVIDER`、`RERANK_*`、`RERANK_MAX_CANDIDATES`、`KB_RERANK_SCORE_THRESHOLD`
- **KB 节点外搜**：`KB_ENABLE_EXTERNAL_SEARCH`、`KB_EXTERNAL_SEARCH_URL`、`KB_EXTERNAL_SEARCH_TIMEOUT`

下列前缀主要服务于 **其它管线**（如外部摄取 / KB 多工具子图中的 `kb_ingest`），**不是** `KnowledgeService` 读 Milvus 时用的那一套，改它们往往解决不了「本 HTTP 向量库」的嵌入维度问题：

- `KB_EMBEDDING_*`、`KB_LLM_*`、`KB_USE_LLM`、`KB_RERANK_ENABLED`（带此前缀的摄取侧 rerank）等

拿不准时以 `knowledge_service.py` 与 `embeddings.py` 里实际读取的 `settings` 字段为准。

## 3. HTTP 层：`knowledge_router`

路由前缀：`router = APIRouter(prefix="/knowledge")`，与 `API_V1_PREFIX` 拼接后为 `**/api/v1/knowledge/...`**。

依赖注入为每个请求构造 `**KnowledgeService()**`（无全局单例，注意连接开销；生产可酌情缓存）。

批量入库：校验列表体、为缺省 `id` 的条目生成 `recipe_{uuid8}`，再调用 `service.add_recipes_batch`：

```109:127:gustobot/interfaces/http/knowledge_router.py
@router.post("/recipes/batch", status_code=201)
async def add_recipes_batch(
    recipes: List[RecipeModel],
    service=Depends(get_knowledge_service),
) -> Dict[str, Any]:
    """Add recipes in batch."""
    try:
        import uuid

        for recipe in recipes:
            if not recipe.id:
                recipe.id = f"recipe_{uuid.uuid4().hex[:8]}"

        result = await service.add_recipes_batch([recipe.dict() for recipe in recipes])
        return {
            "status": "success",
            "message": f"Inserted {result['success']} recipes",
            "statistics": result,
        }
```

`RecipeModel` 字段与入库文本映射一致，包括 `name`、`category`、`difficulty`、`time`、`ingredients`、`steps`、`tips`、`nutrition` 等（见同文件 `RecipeModel` 定义）。

语义检索 HTTP：`POST /search`，请求体 `SearchRequest`，内部 `service.search`：

```132:141:gustobot/interfaces/http/knowledge_router.py
@router.post("/search", response_model=SearchResponse)

    request: SearchRequest,
    service=Depends(get_knowledge_service),

    """Search the vector knowledge base."""
```

### 3.1 向量相关 HTTP 端点一览（前缀均为 `/api/v1/knowledge`）


| 方法     | 路径                     | 作用             | 初学者提示                                |
| ------ | ---------------------- | -------------- | ------------------------------------ |
| POST   | `/recipes`             | 单条菜谱入库         | 无 `id` 时服务端生成 `recipe_` + 短 uuid     |
| POST   | `/recipes/batch`       | 批量入库           | 爬虫、`import_recipes.py` 走这里；注意超时与批次大小 |
| POST   | `/search`              | 仅向量检索          | 不经过 LLM，适合调试「库里到底召回什么」               |
| GET    | `/stats`               | 集合统计 + 切块/模型信息 | 确认是否连上 Milvus、集合是否为空                 |
| DELETE | `/recipes/{recipe_id}` | 按菜谱 id 删向量     | id 与入库时 `recipe_id` 一致               |
| DELETE | `/clear?confirm=true`  | **清空集合**       | 生产极危险，仅测试环境使用                        |


同一份路由文件 `knowledge_router.py` 里还注册了 **Neo4j** 的 `GET /graph`、`POST /graph/qa`。它们和上面的 Milvus 向量接口**共用 URL 前缀**（都是 `/api/v1/knowledge/...`），但**底层不是同一套存储、也不是同一种检索方式**。

#### 「不是同一个库」到底指什么？

这里的「库」指**存数据、做检索的那套后端**，不是泛指「知识」这个概念。


| 对比      | Milvus 向量侧（本文主角）                                                        | Neo4j 图谱侧（同文件另几支 API）                             |
| ------- | ----------------------------------------------------------------------- | ------------------------------------------------- |
| 典型路径    | `POST /knowledge/recipes`、`POST /knowledge/search` 等                    | `GET /knowledge/graph`、`POST /knowledge/graph/qa` |
| 底层系统    | **Milvus**（向量数据库）                                                       | **Neo4j**（图数据库）                                   |
| 里面大致是什么 | 菜谱正文切块后的 **文本 + 向量**，用「和问题像不像」来近邻搜                                      | **节点、边** 组成的图，用 **Cypher / 图上的规则或模板** 来查          |
| 数据是否互通  | 只给 Milvus 导入，**不会**自动进 Neo4j；只建 Neo4j 图，**也不会**被 `/knowledge/search` 搜到 |                                                   |


所以：**口语里都可以叫「知识库」，但工程上往往是多套并行能力**（本文的 Milvus 链、同路由的 Neo4j 链，以及 [RAG.md](RAG.md) 里还提到的 LightRAG、KB 多工具等）。排查「搜不到 / 答不出」时，要先说清是 **向量检索（Milvus）** 没命中，还是 **图谱问答（Neo4j）** 不对——要查的进程、配置和数据准备都不一样。

Neo4j 侧数据模型、`/graph` 与 `/graph/qa`、引导导入与 `recipe_kg` 流水线详见 **[Neo4j库.md](Neo4j库.md)**。

### 3.2 HTTP 与 `KnowledgeService.search` 的参数差异

`POST /search` 的请求体 `**SearchRequest`** 只包含：

- `query`（必填）
- `top_k`（可选，默认 **5**，且 Pydantic 约束为 **1～20**）

因此 **HTTP 层无法传入** `similarity_threshold`、`filter_expr`、`filter_by_similarity`；这些参数仅在 **Python 代码**里调用 `KnowledgeService.search(...)` 时可用（例如 `kb_tools` 从 `state["context"]` 读取 `top_k`、`similarity_threshold`、`filter_expr`）。

调试「阈值是否过严」时：要么改环境变量 `KB_SIMILARITY_THRESHOLD` / `KB_RERANK_SCORE_THRESHOLD` 后重启服务，要么写一小段脚本直接调 `search`，不要指望仅靠 `/search` 的 JSON 体切换行为。

### 3.3 用 curl 做最小联调（本地默认 `8000`）

将 `BASE` 换成你的 `origin + API_V1_PREFIX`（默认 `http://localhost:8000/api/v1`）。

```bash
# 集合是否为空、维度与索引类型
curl -s "${BASE}/knowledge/stats"

# 单条入库（无 id 时服务端生成 recipe_ 前缀）
curl -s -X POST "${BASE}/knowledge/recipes" \
  -H "Content-Type: application/json" \
  -d '{"name":"番茄炒蛋","category":"家常菜","ingredients":["鸡蛋","番茄"],"steps":["打蛋","炒蛋","下番茄炒匀"]}'

# 语义检索（仅向量链路，不经过 LLM）
curl -s -X POST "${BASE}/knowledge/search" \
  -H "Content-Type: application/json" \
  -d '{"query":"鸡蛋怎么做","top_k":3}'
```

批量入库体为 **JSON 数组**，字段需符合 `RecipeModel`（`name` 必填）；大文件请控制单次条数与超时，或直接使用 `scripts/import_recipes.py`。

### 4.2 流程中的主要方法一览（入库与检索）

读源码时可按下面两条链对照（箭头表示调用顺序）：

**入库（写入 Milvus）**

```text
add_recipes_batch
  └─ add_recipe → _format_recipe_document（仅菜谱路径）
add_document（通用文档）
  └─ 合并 metadata（title / name / recipe_id）
        └─ ingest_text（所有入库最终汇聚于此）
             ├─ _split_into_documents（整段 → List[Document]）
             ├─ embedder.embed_documents（块正文 → 向量）
             └─ _store_documents（chunk_id、对齐 metadatas → vector_store.add_documents）
```

**检索**

```text
search
  ├─ embedder.embed_query
  ├─ vector_store.search（可选 filter_expr）
  ├─ 按 KB_SIMILARITY_THRESHOLD 过滤（与 filter_by_similarity、rerank 组合有关）
  ├─ reranker.rerank（若启用）
  └─ 截断 top_k
```

### 4.3 对外入库：`add_document`、`add_recipe`、`add_recipes_batch`

- `**add_document`**：适合「已有标题 + 长正文」的非菜谱场景；会 `setdefault("title", title)`、`setdefault("name", title)`，若传入 `doc_id` 则在没有 `recipe_id` 时写入 `recipe_id`，以便 `_store_documents` 用同一套 `base_id` 规则生成分块主键。  
- `**add_recipe**`：HTTP `RecipeModel` 入库走这条；先 `**_format_recipe_document**`，再带 `recipe_id`、`name`、`category`、`difficulty` 元数据进 `ingest_text`。  
- `**add_recipes_batch**`：对列表逐条解析 `id` / `recipe_id`，否则 `**uuid4()**`，统计 `success` / `error` / `total`。

```144:222:gustobot/infrastructure/knowledge/knowledge_service.py
            doc_id: 可选的逻辑文档 id；当元数据中尚无 ``recipe_id`` 时作为其值写入。

            content: 待切分、嵌入并持久化的正文。
            metadata: 与上述字段合并的额外元数据。

            至少成功写入一个分块时为 ``True``；正文为空或持久化失败时为 ``False``。

        meta.setdefault("name", title)

        """将一条结构化菜谱格式化为文本后入库。

        先用 :meth:`_format_recipe_document` 生成多行中文描述，再附带 ``recipe_id``、菜名、

            recipe_id: 业务侧菜谱主键，写入元数据并参与分块 id 推导。
            recipe_data: 支持 ``name``、``category``、``steps``、``ingredients`` 等常见键；

        metadata = {

            "name": recipe_data.get("name", ""),
            "category": recipe_data.get("category", ""),
            "difficulty": recipe_data.get("difficulty", ""),
        }
        result = await self.ingest_text(document, metadata=metadata)
        return result.get("add_count", 0) > 0

    async def add_recipes_batch(self, recipes: List[Dict[str, Any]]) -> Dict[str, int]:
        """逐条调用 :meth:`add_recipe`，汇总成功与失败条数。

        每条记录的 id 依次尝试 ``recipe["id"]``、``recipe["recipe_id"]``；皆无时生成随机
        UUID，保证可入库。

        Args:
            recipes: 菜谱字典列表，元素含义与 :meth:`add_recipe` 的 ``recipe_data`` 相同。

        Returns:
            字典含 ``success``、``error`` 以及 ``total``（输入列表长度）。

        error_count = 0

            recipe_id = recipe.get("id") or recipe.get("recipe_id") or str(uuid4())
            if await self.add_recipe(recipe_id, recipe):
                success_count += 1
            else:
                error_count += 1
```

### 4.5 入库主干：`ingest_text`

**所有**最终写入 Milvus 的正文都经过这里：先做空白校验，再 `**asyncio.to_thread`** 依次跑 `**_split_into_documents**`、`**embed_documents**`、`**_store_documents**`，避免阻塞事件循环。

```108:141:gustobot/infrastructure/knowledge/knowledge_service.py
    async def ingest_text(
        self,
        text: str,
        *,
        metadata: Optional[Dict[str, Any]] = None,
    ) -> Dict[str, Any]:
        """入库主干：切块 → 批量嵌入 → 写入向量库。

        空字符串或仅空白时直接返回 ``{"add_count": 0, "ids": []}``。切分、嵌入与落库在
        后台线程执行（``asyncio.to_thread``），避免阻塞事件循环。

        Args:
            text: 待入库的完整正文。
            metadata: 写入每个分块的元数据；会影响 :meth:`_store_documents` 中的逻辑 id
                与 ``chunk_id`` 生成。

        Returns:

            ``add_count`` 为 0。
        """

            return {"add_count": 0, "ids": []}

        documents = await asyncio.to_thread(self._split_into_documents, text, metadata or {})
        if not documents:
            return {"add_count": 0, "ids": []}

            [doc.page_content for doc in documents],

        result = await asyncio.to_thread(self._store_documents, documents, embeddings)
```

### 4.7 分块 ID 与写入：`_store_documents`

在 `**ingest_text**` 里于线程中调用，**同步方法**。入参 `**documents`** 与 `**embeddings**` 须**等长**；若任一为空，直接返回 `{"add_count": 0, "ids": [], "stored": False}`。

对每一块：从元数据推导 `**base_id`**（顺序 `**recipe_id` → `id` → `source` → 随机 `uuid4().hex**`），主键 `**chunk_id = f"{base_id}_{index}"**`；并 `**setdefault**` 补齐 `recipe_id`、`chunk_id`、`name`（可用 `title` 兜底）。最后调用 `**vector_store.add_documents**`；成功时返回 `add_count=len(ids)`、`ids` 列表、`stored=True`。

```345:388:gustobot/infrastructure/knowledge/knowledge_service.py
    def _store_documents(
        self,
        documents: List[Document],
        embeddings: List[List[float]],
    ) -> Dict[str, Any]:
        """为每个分块生成唯一 ``chunk_id``、补齐 ``recipe_id`` 等，并批量写入向量库。

        ``base_id`` 优先取元数据 ``recipe_id``，否则 ``id``、``source``，再否则随机 hex；
        每条向量行的主键为 ``{base_id}_{index}``。

        Args:
            documents: 已切好的文档块。
            embeddings: 与 ``documents`` 等长的向量列表。

        Returns:
            含 ``add_count``、``ids``、``stored``；失败或输入为空时 ``add_count`` 为 0。
        """
        if not documents or not embeddings:
            return {"add_count": 0, "ids": [], "stored": False}

        ids: List[str] = []
        contents: List[str] = []
        metadatas: List[Dict[str, Any]] = []

        for index, doc in enumerate(documents):
            metadata = dict(doc.metadata or {})
            base_id = metadata.get("recipe_id") or metadata.get("id") or metadata.get("source") or uuid4().hex
            chunk_id = f"{base_id}_{index}"
            metadata.setdefault("recipe_id", base_id)
            metadata.setdefault("chunk_id", chunk_id)
            metadata.setdefault("name", metadata.get("name") or metadata.get("title") or "")

            ids.append(chunk_id)
            contents.append(doc.page_content)
            metadatas.append(metadata)

        success = self.vector_store.add_documents(
            ids=ids,
            embeddings=embeddings,
            documents=contents,
            metadatas=metadatas,
        )

        return {"add_count": len(ids) if success else 0, "ids": ids, "stored": success}
```

### 4.8 检索：`search`

要点：先按配置扩大 `**recall_k**`（启用 rerank 时），再 `vector_store.search`；相似度过滤；可选 `**reranker.rerank**`；最后截断 `top_k`。

```224:291:gustobot/infrastructure/knowledge/knowledge_service.py
    async def search(
        self,
        query: str,
        *,
        top_k: Optional[int] = None,
        similarity_threshold: Optional[float] = None,
        filter_expr: Optional[str] = None,
        filter_by_similarity: bool = True,
    ) -> List[Dict[str, Any]]:
        """对查询文本做向量检索，并按配置过滤、可选重排。

        典型顺序：查询嵌入 → ``vector_store.search`` 召回；若 ``filter_by_similarity`` 为真
        且配置了阈值，先用向量相似度 ``score`` 过滤。启用 ``Reranker`` 时会把召回上限提高到
        ``settings.RERANK_MAX_CANDIDATES``，精排后再按 ``rerank_score`` 阈值过滤，最后截断为
        ``top_k``。未启用重排且 ``filter_by_similarity`` 为假时，阈值在排序后阶段再应用
        （见实现中的分支）。

        Args:
            query: 用户问题或检索语句；空或纯空白返回 ``[]``。
            top_k: 最终返回条数上限；默认 ``settings.KB_TOP_K``。
            similarity_threshold: 相似度下限；``None`` 时用 ``settings.KB_SIMILARITY_THRESHOLD``。
            filter_expr: 向量库原生过滤表达式（如 Milvus 表达式），由 ``VectorStore`` 解析。
            filter_by_similarity: 控制相似度阈值在流水线前半段是否生效；与是否启用 reranker
                组合时行为不同，阅读本方法实现可对照。

        Returns:
            命中项字典列表，长度不超过 ``top_k``；字段名含 ``score``，启用重排时另有
            ``rerank_score`` 等（以实际返回为准）。
        """
        if not query or not query.strip():
            return []

        top_k = top_k or settings.KB_TOP_K
        similarity_threshold = (
            similarity_threshold if similarity_threshold is not None else settings.KB_SIMILARITY_THRESHOLD
        )

        # 如果启用 reranker，先召回更多候选文档
        recall_k = top_k
        if self.reranker.enabled:
            recall_k = settings.RERANK_MAX_CANDIDATES  # 召回更多文档用于重排

        embedding = await asyncio.to_thread(self.embedder.embed_query, query)
        results = await asyncio.to_thread(
            self.vector_store.search,
            embedding,
            recall_k,  # 使用更大的召回数量
            filter_expr,
        )

        candidates = results
        if filter_by_similarity and similarity_threshold is not None:
            candidates = [r for r in candidates if r.get("score", 0.0) >= similarity_threshold]

        # 使用 reranker 精排
        if candidates and self.reranker.enabled:
            candidates = await self.reranker.rerank(query, candidates, top_k)

        if self.reranker.enabled:
            candidates = [
                r
                for r in candidates
                if r.get("rerank_score", 0.0) >= settings.KB_RERANK_SCORE_THRESHOLD
            ]
        elif not filter_by_similarity and similarity_threshold is not None:
            candidates = [r for r in candidates if r.get("score", 0.0) >= similarity_threshold]

        return candidates[:top_k]
```

`**filter_by_similarity` 与 rerank 的组合**：启用 rerank 时，向量分数过滤发生在精排**之前**；未启用 rerank 且 `filter_by_similarity=False` 时，阈值会在最后阶段再滤一遍（见上分支）。扩展自定义调用时要对照该顺序调参。

本节的「嵌入模型」特指 `**KnowledgeService` 写入 / 检索 Milvus 时调用的那一个**：由 `EMBEDDING_*` 配置、`OpenAICompatibleEmbeddings` 实现，经 OpenAI 官方 SDK 访问 `**POST .../embeddings`** 形态的服务。

### 6.1 在链路中的角色

- **入库**：每个文本块（chunk）调用一次批量路径 `embed_documents`，得到与块一一对应的向量，再写入 Milvus 的 `embedding` 列。  
- **检索**：用户问题（或 HTTP `/search` 的 `query`）调用 `embed_query`，得到**一条**查询向量，与库内向量做近邻搜索。  
- **必须用同一套配置**：同一 `EMBEDDING_MODEL`、同一 `EMBEDDING_BASE_URL`（同一服务商与模型权重）。若入库用模型 A、查询用模型 B，向量空间不一致，近邻结果**没有可靠语义**。  
- **与 LLM 解耦**：对话里生成回答的 LLM（`OPENAI_API_KEY` 等）可以和嵌入不同厂商；但 `KnowledgeService` 里密钥缺省时会把 `**EMBEDDING_API_KEY` 回落到 `LLM_API_KEY`**，仅当两者指向**兼容的嵌入服务**时才建议共用。

```82:88:gustobot/infrastructure/knowledge/knowledge_service.py
        self.embedder = OpenAICompatibleEmbeddings(
```

### 6.2 配置项（与 `settings.py` 对应）


| 变量                    | 作用                                         | 默认（以源码为准）                                 |
| --------------------- | ------------------------------------------ | ----------------------------------------- |
| `EMBEDDING_MODEL`     | 传给 `embeddings.create(model=...)` 的模型名     | `text-embedding-3-small`                  |
| `EMBEDDING_BASE_URL`  | API 根地址；`None` 时 SDK 使用官方 OpenAI           | `None`（即官方端点）                             |
| `EMBEDDING_API_KEY`   | 嵌入专用密钥；为空则用 `LLM_API_KEY`                  | `None`                                    |
| `EMBEDDING_DIMENSION` | **期望**维度：传给 `VectorStore` 建表 / 校验，并与日志告警对照 | `1536`（与 `text-embedding-3-small` 默认维度一致） |


说明：

- `**EMBEDDING_PROVIDER`** 在配置里存在，但 `**KnowledgeService` 并不根据它分支**；Milvus 这条链路只认上面的模型名 + base_url + key。换「供应商」时，实际改的是 **base_url / model / key**，不必指望改 `EMBEDDING_PROVIDER` 单独生效。  
- `**EMBEDDING_DIMENSION`** 在 `OpenAICompatibleEmbeddings` 里**不会**用来截断或填充向量：若真实返回长度与配置不一致，只会 **打 warning**，向量原样写入 Milvus；若与集合 `dim` 不一致，会在 Milvus 侧 **插入 / 检索失败**。因此应以**模型文档中的输出维度**为准填 `EMBEDDING_DIMENSION`。  
- 部分模型支持**可配置输出维度**（如部分 OpenAI embedding 模型通过 API 参数缩维）；若你启用了缩维，**环境变量、Milvus 集合维度、请求参数**三者必须一致，否则仍会失败。

### 6.3 兼容的服务形态（OpenAI Embeddings API）

实现上调用的是 `**openai.OpenAI` + `client.embeddings.create(model=..., input=batch)`**，因此只要对方提供 **OpenAI 兼容的 `/v1/embeddings`**（路径以服务商文档为准，通常由 `base_url` 指向的根已经包含 `/v1` 前缀约定），即可接入，例如：

- OpenAI 官方；  
- Azure OpenAI（需使用 Azure 提供的 base_url 与部署名，具体以 Azure 文档为准）；  
- 国内聚合网关、兼容层（如部分云厂商、自建 OneAPI 等）——**务必核对模型名、维度与是否支持批量 `input` 数组**。

**中文菜谱场景**：多数通用多语言 embedding 对中文可用；若召回明显弱于预期，可在同数据上对比 1～2 个模型，再固定配置做全量重灌。

### 6.4 请求行为与边界（`_embed` 内部）

- **分批**：`max_batch_size` 默认 **64**，长列表会切成多批调用 `embeddings.create`，避免单次请求过大。  
- **超时**：`request_timeout` 默认 **60** 秒（秒级浮点）。  
- **空字符串**：会先 `strip()`；若某条为空，会改成**单个空格**再请求，避免部分厂商对空 `input` 报错，同时用 `index_map` **保持与原始下标对齐**。  
- **条数校验**：返回向量条数与请求条数不一致会 `**RuntimeError`**，并打 error 日志。  
- **缺向量兜底**：若某位置最终仍无向量，会用 **零向量** 填充（维度取首条成功向量或 `dimension`）。这会导致「静默劣质向量」，一般不应依赖该路径；应优先修 API / 网络 / 配额问题。  
- **代理**：若环境变量里存在 httpx 不支持的代理 scheme（如 `socks://`），构造客户端可能失败；此时会降级为 `**httpx.Client(trust_env=False)`** 再建 `OpenAI` 客户端，避免因代理把整个知识库拖死（见 `embeddings.py` 中 `ValueError` 分支）。

### 6.5 与 `MILVUS_METRIC_TYPE` 的关系

嵌入向量本身不决定 Milvus 用 **IP / COSINE / L2**；但 **分数含义和阈值调参**与度量绑定（见第 1.2 节）。默认 `**IP`** 时，若向量已 L2 归一化，内积与余弦单调相关，工程中常见；若你改用其它度量或换模型，需重新观察 `score` 分布并调整 `KB_SIMILARITY_THRESHOLD`。

### 6.6 更换嵌入模型时的建议步骤

1. 查服务商文档，确认 **模型名** 与 **输出维度**。
2. 将 `EMBEDDING_MODEL`、`EMBEDDING_BASE_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_DIMENSION` 改成新组合。
3. **新建 Milvus collection**（或清空后重建），使 `**dim` 与新维度一致**；旧向量与新模型**不可混用**。
4. **全量重新入库**。
5. 用固定用例跑 `/search` 与对话 KB，必要时重调 `**KB_SIMILARITY_THRESHOLD`** 与重排阈值。

### 6.7 对外 API 方法

```75:96:gustobot/infrastructure/knowledge/embeddings.py
    def embed_documents(self, texts: Sequence[str]) -> List[List[float]]:
        """批量将文本转为向量列表，顺序与 ``texts`` 一致。

        Args:
            texts: 任意可迭代字符串序列。

        Returns:
            与 ``texts`` 等长的浮点向量列表；详见 :meth:`_embed` 对空串、失败回退的说明。
        """
        return self._embed(texts)

    def embed_query(self, text: str) -> List[float]:
        """将单条查询文本转为一条向量（检索侧常用）。

        Args:
            text: 用户问题或查询句。

        Returns:
            一维浮点列表；输入异常或 API 无返回时可能为空列表，调用方需自行兜底。
        """
        embeddings = self._embed([text])
        return embeddings[0] if embeddings else []
```

`embed_query` 与 `embed_documents` **走同一套 `_embed` 与同一 `model`**，不区分「查询专用」模型；若你希望 query/doc 使用不同模型，需要改代码或拆两条服务（当前仓库未提供该能力）。

## 7. 重排：`Reranker`

本节对应 `gustobot/infrastructure/knowledge/reranker.py`，由 **`KnowledgeService.search`** 在 **Milvus 向量召回之后**调用（顺序见 **§4.8**）：先按 `RERANK_MAX_CANDIDATES` 多召回，再 **`reranker.rerank`**，最后按 **`KB_RERANK_SCORE_THRESHOLD`** 过滤并截断 `top_k`。

### 7.1 为什么要重排？和向量检索分工是什么？

- **向量检索（embedding + 近邻）**：把 query 和文档块压成向量，按几何距离找「大致相近」的块；**快、可海量**，但对「细粒度相关性」（谁更直接回答这个问题）往往不如 **Cross-Encoder / 专用 rerank 模型**。  
- **重排（rerank）**：把 **query + 每条候选正文** 交给另一套模型或 API，输出 **相关性分数**，再**按分数排序**。典型用于：**向量先粗排 20 条，rerank 精排出前 5 条** 给 LLM 或返回给调用方。

本项目的 `Reranker` **不替代 Milvus**：没有重排服务时，检索链路仍可用，只是跳过精排步骤。

### 7.2 何时真正启用？（`enabled` 条件）

构造时（`Reranker.__init__`）：

- `RERANK_ENABLED=False` → 打日志 `disabled`，**不重排**。  
- `RERANK_ENABLED=True` 但 **`RERANK_PROVIDER` 为空或 `RERANK_API_KEY` 为空** → 打 warning，**强制 `enabled=False`**，避免误连网。

之后 **`rerank(...)` 始终可安全调用**：未启用时等价于 **`documents[:top_k]`**（保持向量顺序截断）。

### 7.3 `rerank` 主流程与失败策略

```79:100:gustobot/infrastructure/knowledge/reranker.py
        if not self.enabled or not documents:
            return documents[:top_k]

        try:
            if self.provider == "custom":
                ranked = await self._custom_rerank(query, documents, top_k)
            elif self.provider == "cohere":
                ranked = await asyncio.to_thread(self._cohere_rerank, query, documents, top_k)
            elif self.provider == "jina":
                ranked = await self._jina_rerank(query, documents, top_k)
            elif self.provider == "voyage":
                ranked = await self._voyage_rerank(query, documents, top_k)
            else:
                logger.warning(f"Unsupported reranker provider: {self.provider}")
                return documents[:top_k]

            if ranked:
                return ranked
        except Exception as exc:
            logger.error("Reranker failed: %s", exc, exc_info=True)

        return documents[:top_k]
```

要点：

- **`provider`** 为 **`custom` / `cohere` / `jina` / `voyage`** 之一时走对应实现；其它字符串 → warning + 回退截断。  
- **任意异常**（网络、4xx/5xx、`cohere` 未安装等）→ 打 error 日志，**回退 `documents[:top_k]`**，检索主链路不中断。  
- **`cohere`** 使用官方同步 SDK，在 **`asyncio.to_thread`** 里跑，避免阻塞 FastAPI 事件循环；**`custom` / `jina` / `voyage`** 使用 **`httpx.AsyncClient`**（`trust_env=False`，与嵌入侧类似，减少环境代理干扰）。

### 7.4 各 `provider` 行为摘要

| `RERANK_PROVIDER` | 请求方式 | 说明 |
|-------------------|----------|------|
| `custom` | `POST {RERANK_BASE_URL}{RERANK_ENDPOINT}` | 默认请求体贴近 **DashScope 风格**：`model`、`input.query`、`input.documents`、`parameters`（含 `return_documents`、`top_n`）；解析 `output.results` 里每项的 `index` 与 `relevance_score` 或 `score`。**必须配置 `RERANK_BASE_URL`**，否则直接回退截断。 |
| `jina` | 固定 `https://api.jina.ai/v1/rerank` | `Bearer` 鉴权；`top_n` 取 `min(RERANK_TOP_N 或 top_k, len(documents))`；模型默认可回落到 `jina-reranker-v1-base-en`（见源码）。 |
| `voyage` | 固定 `https://api.voyageai.com/v1/rerank` | 请求字段为 `top_k`（与 Jina 的 `top_n` 不同）；模型默认可回落 `rerank-lite-1`。 |
| `cohere` | 官方 `cohere` SDK `client.rerank` | 需安装 **`cohere`** 包；模型默认可回落 `rerank-english-v3.0`。 |

文档正文统一从每条字典的 **`content` 或 `document`** 取出字符串列表传给服务商；与 `VectorStore.search` 返回的 `content` 字段一致。

### 7.5 结果合并：`_process_rerank_results` 与 `rerank_score`

Jina / Voyage / Cohere 路径在拿到厂商返回的 **`index` + 分数** 后，经 **`_process_rerank_results`** 合并回原始 `documents` 的拷贝，并写入 **`rerank_score`**（浮点）。**未出现在厂商结果列表中的文档**会按 **`chunk_id` 或 `id` 去重后追加在末尾**，再 **`[:top_k]`**，避免「召回有、但 rerank API 没返回」的条目被静默丢弃。

`custom` 路径在 `_custom_rerank` 内做了**同样思路**的合并（`seen_ids` + 追加未出现文档）。

### 7.6 与 `KnowledgeService.search` 相关的配置（Milvus 检索链）

以下由 **`KnowledgeService` + `Reranker`** 实际使用（与 **`KB_*` 前缀的 kb_ingest 重排**不是同一套，勿混）：

| 变量 | 作用 |
|------|------|
| `RERANK_ENABLED` | 总开关 |
| `RERANK_PROVIDER` | `custom` / `cohere` / `jina` / `voyage` |
| `RERANK_API_KEY` | 各服务商 Bearer / SDK 密钥 |
| `RERANK_BASE_URL` | **`custom` 必填**；其它 provider 固定 URL，此项可忽略 |
| `RERANK_ENDPOINT` | 拼在 `BASE_URL` 后，默认 `/rerank` |
| `RERANK_MODEL` | 传给 API 的模型名（如 `bge-reranker-large`） |
| `RERANK_MAX_CANDIDATES` | **仅 `KnowledgeService.search`**：启用 rerank 时 Milvus **先召回条数**（再精排） |
| `RERANK_TOP_N` | 传给 rerank API 的「参与精排/返回」上限，与 `top_k` 取 `min` |
| `RERANK_TIMEOUT` | HTTP/SDK 调用超时（秒） |
| `KB_RERANK_SCORE_THRESHOLD` | 精排后按 **`rerank_score`** 再滤一道；过严会清空结果 |

`settings` 中的 **`RERANK_SCORE_FUSION_ALPHA`** 在当前 `reranker.py` **未参与计算**，属预留或它处用途；以源码为准。

### 7.7 调参与排错提示

- **`KB_RERANK_SCORE_THRESHOLD` 过高**：重排后无条目通过，最终 `search` 返回空；可先**降低阈值**或临时关 `RERANK_ENABLED` 对比。  
- **`RERANK_MAX_CANDIDATES` 过小**：粗排候选太少，rerank **无从优化**；可适当增大，注意 API 费用与延迟。  
- **`custom` + 第三方格式不一致**：若响应不是 `output.results` + `index` + `relevance_score`/`score`，可能解析不到分数或顺序异常；需对照 **`_custom_rerank`** 改 payload 或改解析逻辑。  
- **日志**：失败时搜 `Reranker failed`；未启用时搜 `Reranker disabled` / `missing provider or API key`。

更细的默认值与示例见 **[环境变量与配置说明.md](环境变量与配置说明.md)**。

## 12. 注意事项、排错与进阶认知

### 12.1 配置与模型

- **嵌入维度 / 换模型**：详见 **第 6 节**；`EMBEDDING_DIMENSION` 必须与模型真实输出维度和 Milvus `dim` 一致；换模型需 **新集合 + 全量重灌** 并重调相似度阈值。  
- **嵌入与 LLM 可否不同厂商**：可以，但要在效果与延迟、配额、故障面之间权衡；排查问题时记得**两边 API 都要通**。`EMBEDDING_API_KEY` 为空时会用 `LLM_API_KEY`，不要误以为只配了聊天密钥就会自动走「正确的嵌入服务」。

### 12.2 路由与依赖注入

- `**get_knowledge_service` 每次 new**：每个命中路由的请求可能新建 `KnowledgeService()`，进而连接 Milvus。开发环境问题不大；**高 QPS 生产**应考虑单例或连接池，避免连接风暴与重复建连开销。  
- **异步与线程**：`KnowledgeService` 用 `asyncio.to_thread` 跑阻塞的 Milvus/嵌入调用，避免卡死整个 FastAPI 事件循环；若嵌入 API 极慢，仍会占用线程池，需配合超时与限流。

### 12.3 数据与业务语义

- **重复导入同一 `recipe_id`**：当前 `add_documents` 为 **insert**，主键 `chunk_id` 若与已存在主键冲突，行为取决于 Milvus 与主键是否变化；若每次导入生成新 `recipe_id` 或新 chunk 主键，可能产生**重复语义文档**。生产上常需要「幂等 upsert」或先删后插策略（见第 13 节）。  
- **按 `recipe_id` 删除**：Milvus 行主键是 **分块 id**（`{recipe_id}_{0}`、`{recipe_id}_{1}`、…），而 `VectorStore.delete_documents` 当前使用表达式 `**id in [...]`**。`KnowledgeService.delete_recipe` 传入的是业务 `**recipe_id` 字符串**，与分块主键字面量往往**不一致**，可能导致「删了但库里还在」或 404。若你在环境中遇到该现象，应按 `recipe_id` 标量字段批量删除或先查出所有 chunk 主键再删（演进方向见第 13 节「幂等与更新」）。  
- **空正文**：`_format_recipe_document` 若得到空串，`ingest_text` 直接返回 0 条，批量里会计入 **error**，HTTP 仍可能返回 201——要养成看 `**statistics.error`** 的习惯。  
- `**ingredients` 类型**：`RecipeModel` 里是 `List[str]`；若脚本传入非列表，可能在 Pydantic 层 422。导入前用 `--dry-run` 看 JSON。

### 12.4 检索与阈值

本节对应 `KnowledgeService.search` 里 **Milvus 召回 →（可选）向量分过滤 →（可选）重排 →（可选）重排分过滤 → 截断 `top_k`**。调参前要牢记：**`score` 的含义随 `MILVUS_METRIC_TYPE` 而变**（如 `IP` 与 `COSINE` 下数值尺度不同），**不要照搬网上其它项目的阈值**；应以本环境实际分布为准逐步试。

#### 12.4.1 `KB_SIMILARITY_THRESHOLD`（向量相似度下限）

- **作用对象**：Milvus 返回的每条命中上的 **`score`**（向量相似度/距离经 SDK 转换后的分值）。  
- **何时参与过滤**：由参数 **`filter_by_similarity`** 与 **是否启用 rerank** 共同决定（见下节 **12.4.2**）。  
- **「过严」的现象**：过滤后 `candidates` 为空，最终 `search` 返回 `[]`；对话里 **`kb_tools`** 会落到「知识库中没有找到」类兜底。  
- **怎么松**：  
  - **改环境变量** `KB_SIMILARITY_THRESHOLD`（降低），重启进程；或  
  - **在代码里**调用 `search(..., similarity_threshold=更小的值)`；  
  - **关闭向量阶段阈值**：`search(..., filter_by_similarity=False)`（仅当你明确要在**不重排**或**重排后**再靠别的逻辑筛时再配合使用，见 12.4.2）。

**HTTP `POST /knowledge/search`** 的请求体**不能**传 `similarity_threshold` / `filter_by_similarity`，只能使用 **`KnowledgeService.search` 的默认值**（阈值来自 `settings`）。因此**纯用 curl 调 `/search` 无法单独调试「关阈值」**，需要改配置或写脚本调 `search`。

#### 12.4.2 `filter_by_similarity` 与重排组合（读源码调参）

下面与 `knowledge_service.py` 中实现顺序一致：

**启用 rerank（`reranker.enabled`）时**

1. Milvus 召回 **`recall_k = RERANK_MAX_CANDIDATES`**（扩大粗排池）。  
2. 若 **`filter_by_similarity=True`**（默认）且 `similarity_threshold` 非空：用 **`score >= KB_SIMILARITY_THRESHOLD`** 过滤**一遍**（在重排**之前**）。  
3. 对剩余候选调用 **`reranker.rerank`**（内部再截一段，见 **§7**）。  
4. 再用 **`rerank_score >= KB_RERANK_SCORE_THRESHOLD`** 过滤。  
5. 最后 **`return candidates[:top_k]`**。

因此：**向量阈值过严**会导致进入重排的条数为 0；**重排阈值过严**会导致重排后又被删光。两者要**分开**排查。

**未启用 rerank 时**

- 若 **`filter_by_similarity=True`**：在 Milvus 召回后立刻按 **`score`** 过滤。  
- 若 **`filter_by_similarity=False`**：不在前面滤，只在最后（`return` 前）再按 **`score`** 滤一遍（见 `elif not filter_by_similarity and similarity_threshold is not None` 分支）。

**`kb_tools` 节点**：只传入 `top_k`、`similarity_threshold`、`filter_expr`（见 `kb_tools/node.py`），**不传 `filter_by_similarity`**，故始终为 **`True`**。要在对话路径上试 `filter_by_similarity=False` 必须改节点或封装。

#### 12.4.3 重排相关：`RERANK_MAX_CANDIDATES` 与 `KB_RERANK_SCORE_THRESHOLD`

- **`RERANK_MAX_CANDIDATES`**：仅在 **启用 rerank** 时作为 Milvus **`limit`**。过小则粗排候选太少，重排**没有足够材料**可纠偏；过大则延迟与费用上升。  
- **`KB_RERANK_SCORE_THRESHOLD`**：只作用于 **`rerank_score`**（重排 API 写入的字段）。**与 `score` 不可混谈**——二者来源不同，数值范围也可能完全不同。  
- **重排 API 失败**（网络、4xx/5xx、`cohere` 未安装等）：`Reranker.rerank` **捕获异常**，打 **`Reranker failed`** 日志，并回退为 **`documents[:top_k]`**（保持**向量召回顺序**截断）。此时**没有**可靠的 `rerank_score`，后续 **`KB_RERANK_SCORE_THRESHOLD` 过滤**若仍开启，可能因缺字段或分数为 0 而把结果**再次滤光**——若你观察到「一报错就永远空」，可结合日志看是否属于这种情况，并考虑临时调低重排阈值或关闭重排对比。

#### 12.4.4 `filter_expr`（Milvus 布尔表达式）

- **作用**：在向量检索阶段把结果限制在符合标量条件的子集（如 `category == "家常菜"`）。由 **`VectorStore.search`** 传给 Milvus；表达式语法须符合 **Milvus** 规范。  
- **写错的后果**：  
  - 语法非法：驱动/Milvus 可能抛错；`vector_store.search` 内 **catch 后返回 `[]`**（并打日志），表现像「什么都搜不到」。  
  - 条件过严或字段名/取值与入库不一致：**合法但 0 条命中**。  
- **调试建议**：  
  - **HTTP `/search` 当前不传 `filter_expr`**，需在 **Python** 里调 `KnowledgeService.search(..., filter_expr="...")`，或给 **`kb_tools` 的 `context`** 传 `filter_expr`（若你的路由会填这个字段）。  
  - 从**最简单**的表达式开始（如单字段等值），确认有返回后再叠条件。  
  - 字段名必须与 **Milvus Schema** 一致（`recipe_id`、`name`、`category`、`difficulty` 等），字符串注意引号与转义。

### 12.5 与其他「知识」别混

- **Neo4j `recipe_kg`**：自然语言图谱问答，数据在图数据库，不靠 Milvus 向量检索；详见 [Neo4j库.md](Neo4j库.md)。  
- **LightRAG**：`lightrag_router` + `customer_tools`，另一条管线。  
用户说「知识库搜不到」时，先确认走的是 **KB 子图 / Milvus** 还是 **图谱 / LightRAG**。

### 12.6 自查清单（建议打印或收藏）


| 现象                        | 建议检查顺序                                                        |
| ------------------------- | ------------------------------------------------------------- |
| 批量导入 5xx                  | 后端日志；Embedding API 是否通；Milvus 是否起；维度与 collection 是否一致         |
| 导入 201 但 `error` > 0      | 单条是否空正文；字段是否不符合 `RecipeModel`；Milvus insert 是否失败（看日志）         |
| `/search` 永远空             | `GET /stats` 是否 0 条；阈值是否过高；collection 名是否与环境一致                |
| `DELETE /recipes/{id}` 无效 | 当前实现按主键 `id` 删除，与分块主键 `{recipe_id}_n` 可能不一致；见 12.3            |
| 对话里 KB 答不出                | `kb_tools` 是否被路由到；`KnowledgeService()` 配置是否与导入时一致；是否启用了联网仍无结果 |
| 只有部分菜搜不到                  | 切块是否把关键信息切到另一块；问题表述与正文用词差异大；考虑重排或改写 query                     |

## 13. 未来可能的优化方向

以下为**演进建议**，非当前实现承诺；落地前需结合数据量、预算与 SLA 评估。

1. **KnowledgeService 生命周期**：进程内单例或 LRU 缓存 + 显式 `close`，复用 Milvus 连接；与 FastAPI `lifespan` 挂钩。
2. **幂等与更新**：按 `recipe_id` **删除旧 chunk 再写入**，或 Milvus **upsert** 策略，避免重复灌库；支持「部分字段更新」。
3. **批量导入性能**：路由层支持更大 batch 时，在 `add_recipes_batch` 内对嵌入做 **真正的批量**（减少 HTTP 往返嵌入服务），或对同一批文本合并 `embed_documents` 调用。
4. **可观测性**：对嵌入、Milvus、rerank 分段打点（延迟、错误率、空结果率）；关键路径 trace id 贯穿。
5. **检索参数配置化**：`vector_store.search` 里 `**nprobe`**、索引 `nlist` / HNSW `M`、`efConstruction` 等写入 `settings`，按环境调优。
6. **混合检索**：关键词（BM25/SQL）+ 向量融合，改善「专有名词、菜名精确匹配」场景。
7. **Query 变换**：同义词扩展、多查询召回、HyDE 等（与 Agent 总览中 RAG 演进一致）。
8. **内容治理**：脏数据检测、重复菜谱合并、多语言统一、营养/步骤结构化字段的校验。
9. **安全**：`/clear` 等危险操作加鉴权或仅内网；生产关闭或强确认。
10. **评估集**：固定问题集 + 期望命中菜谱 id，对 embedding/阈值/rerank 做回归。
