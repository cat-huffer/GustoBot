## 1. 系统要求

| 项目 | 最低建议 | 说明 |
|------|----------|------|
| Python | 3.9+（`pyproject.toml` 为 `>=3.9`；镜像为 3.10） | 本地开发 / 非容器运行 |
| 内存 | 8GB+ | 同时跑 LLM 调用、Milvus、Neo4j 时更稳 |
| 磁盘 | 20GB+ 可用 | `data/`、向量索引、镜像与卷 |
| Docker | Docker 20+，Compose V2 | `docker compose` 命令 |

**依赖服务（按功能启用）**

- **Redis**：缓存与会话相关能力  
- **Milvus + etcd + minio**：向量检索（Compose 中为 standalone Milvus）  
- **Neo4j**：菜谱图谱与 Agent 子图  
- **MySQL**：Text2SQL / 结构化菜谱数据  
- **kb_postgres（pgvector）**：知识库向量与结构化检索  
- **kb_ingest**：独立摄入服务（Excel 等），默认端口见下表

## 2. 服务与端口（Compose）

以下为仓库 **`docker-compose.yml`** 中常见映射（若你修改过 `ports`，以本机为准）。

| 服务名 | 说明 | 宿主机端口（默认） |
|--------|------|-------------------|
| `backend` | FastAPI（`gustobot.main:application`） | **8000** |
| `neo4j` | 图数据库（Browser / Bolt） | **17474** → 7474，**17687** → 7687 |
| `mysql` | MySQL 8 | **13306** → 3306 |
| `redis` | Redis 7 | **6379** |
| `milvus` | Milvus standalone | **19530**、9091 |
| `minio` | Milvus 依赖 | **9000**、9001 |
| `kb_postgres` | pgvector | **5433** → 5432（可用 `KB_PG_PORT` 覆盖） |
| `kb_ingest` | 摄入服务 | **8100** → 8000（可用 `KB_INGEST_PORT` 覆盖） |

容器内后端通过服务名访问依赖，例如 `NEO4J_URI=bolt://neo4j:7687`、`MILVUS_HOST=milvus`。**`.env` 需与 Compose 中变量一致**，并勿将密钥提交到 Git。

## 3. Docker Compose 部署（推荐）

### 3.1 准备环境变量

```bash
cp .env.example .env
# 编辑 .env：至少配置 LLM_API_KEY、LLM_BASE_URL、LLM_MODEL 等
```

构建阶段若开启 **`INIT_LIGHTRAG_ON_BUILD=true`**，需要在构建时能访问到 **LLM / Embedding**（密钥通过构建参数传入，**勿在 CI 日志中打印**）。详见 [LightRAG服务指南.md](LightRAG服务指南.md)。

### 3.2 启动全栈

在仓库根目录：

```bash
docker compose up -d --build
```

查看后端日志：

```bash
docker compose logs -f backend
```

**说明**

- `backend` 的 `depends_on` 包含 **neo4j、redis、milvus**。**MySQL、kb_postgres、kb_ingest** 等需完整能力时请确保一并启动（例如 `docker compose up -d` 不带服务名即启动文件中全部服务，或按需列出服务名）。
- 开发模式下 Compose 中后端命令常带 **`--reload`**，并挂载 `./gustobot`；**生产**应改为多 worker、去掉 reload，并避免将源码目录以可写方式挂进容器（见第 7 节）。

### 3.3 与文档中旧示例的差异

若你曾参考过名为 `gustobot`/`server` 的 Compose 服务，**本仓库实际服务名为 `backend`**；Neo4j 浏览器端口为 **17474** 而非 7474。请以当前 `docker-compose.yml` 为准。

## 4. 本地 Python 启动

### 4.1 依赖

```bash
python -m venv venv
# Windows: venv\Scripts\activate
# Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
```

### 4.2 启动方式

- **前后端一起（开发）**：`python scripts/start_chatbot.py`（后端 uvicorn + 前端 Vite，见脚本内说明）。  
- **仅后端**：`python -m uvicorn gustobot.main:application --reload --host 0.0.0.0 --port 8000`  
- 根目录 **`start_chatbot.py`** 为薄封装，会转调 `scripts/start_chatbot.py`。

需自行启动本机 **Redis、Milvus、Neo4j、MySQL** 等，并使 `.env` 中的 host/port 指向可达地址。

## 5. 构建说明与 LightRAG

- **`Dockerfile`** 多阶段：`target: server` 为后端镜像；Neo4j 使用 **`neo4j_seeded`** 等目标（见文件后部）。  
- **`INIT_LIGHTRAG_ON_BUILD`**：为 `true` 且提供 **`LLM_API_KEY`** 时，构建过程中会运行 `scripts/init_lightrag.py` 并将结果同步到镜像内 `data/lightrag`（具体逻辑以 Dockerfile 为准）。  
- 运行时 **`LIGHTRAG_WORKING_DIR`** 默认 `./data/lightrag`，Compose 通常挂载 `./data:/app/data`。

## 6. 验证与访问地址

| 用途 | URL |
|------|-----|
| OpenAPI（Swagger） | `http://localhost:8000/docs` |
| 根路径 | `http://localhost:8000/` → 重定向到 `/docs`（见 `gustobot/main.py`） |
| 简单状态 | `GET /api` |
| 健康检查 | `GET /health` → `{"status":"healthy","version":...}` |
| 统一聊天 API | `POST /api/v1/chat/` 等（见 `interfaces/http/v1/chat.py`） |

**前端**：仓库 `web/` 为 Vite 应用，开发时常用 **`npm run dev`**（端口多为 5173），与后端分离；生产可将构建产物由 Nginx 托管。

**CORS**：当前 `main.py` 中对 CORS 多为开发向宽松配置；生产请按域名收紧。若代码中未读取 `CORS_ORIGINS`，请以实际 `gustobot/main.py` 为准。

## 7. 生产环境要点

### 7.1 进程模型

使用 **Gunicorn + Uvicorn Worker** 示例：

```bash
pip install gunicorn
gunicorn gustobot.main:application -k uvicorn.workers.UvicornWorker -w 4 -b 0.0.0.0:8000 --timeout 120
```

根据 CPU、同步阻塞调用比例调整 `workers` 与 `timeout`。

### 7.2 Nginx 与流式接口

对 **SSE / 流式聊天** 需关闭代理缓冲、拉长读超时，例如：

```nginx
location /api/v1/chat/stream {
    proxy_pass http://127.0.0.1:8000;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

LightRAG 流式：`/api/v1/lightrag/query-stream`，同样建议 **`proxy_buffering off`**。

### 7.3 上传与限流

上传大小等与 **`FILE_UPLOAD_MAX_MB`**（及反向代理 `client_max_body_size`）对齐。详见配置说明与 [环境变量与配置说明.md](环境变量与配置说明.md)。

### 7.4 HTTPS

使用 Let’s Encrypt / 云厂商证书，在 Nginx 或入口网关上终止 TLS。

## 8. 故障排查

| 现象 | 处理方向 |
|------|----------|
| `LLM_API_KEY` / 鉴权失败 | 检查 `.env`；Compose 内常将 `OPENAI_API_KEY` 映射自 `LLM_API_KEY` |
| 端口被占用 | 修改 `ports` 或停止占用进程 |
| Milvus / Neo4j 连接失败 | `docker compose ps`；确认服务名与 `MILVUS_HOST`、`NEO4J_URI` 与运行环境一致（容器内用服务名，本机用 localhost + 映射端口） |
| 413 上传过大 | 提高 `FILE_UPLOAD_MAX_MB` 与 Nginx `client_max_body_size` |
| LightRAG 空结果 | 索引是否生成、`LIGHTRAG_WORKING_DIR` 是否挂载正确；见 [LightRAG服务指南.md](LightRAG服务指南.md) |
| 数据库迁移 | 本项目未必使用 Alembic；以仓库内实际迁移脚本与文档为准 |

**日志**

- Compose：`docker compose logs -f backend`  
- 本机：终端输出；若配置了文件日志则查看对应路径
