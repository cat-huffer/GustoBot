# 路由提示词与分类说明

本文系统说明 **主 LangGraph**（`lg_builder`）中的 **意图路由**、各分支 **应答提示词**，以及 **知识库子图**、**图谱多工具子图** 内与「分类 / 规划 / 选工具」相关的提示词。修改路由或分类行为时，请与此文、[智能体路由速查.md](智能体路由速查.md)、测试用例及源码对照。

**权威源码**：

- 主图提示词常量：`gustobot/application/agents/lg_prompts.py`
- 主图编排与路由逻辑：`gustobot/application/agents/lg_builder.py`
- 路由结构化类型：`gustobot/application/agents/lg_states.py` → `Router`
- 图谱侧提示词：`gustobot/application/agents/kg_sub_graph/prompts/kg_prompts.py`
- KB 多工具内嵌提示：`gustobot/application/agents/kg_sub_graph/agentic_rag_agents/workflows/multi_agent/multi_tool.py`

---

## 1. 概念分层：三层「路由」不要混用

| 层级 | 作用 | 典型输出 |
|------|------|----------|
| **L1 主路由** | 用户一句问话 → 主图六大分支之一 | `Router.type`（如 `kb-query`、`graphrag-query`） |
| **L2a KB 子路由** | 已进入 `kb-query` → 选 postgres / milvus / 外搜等 | `KBRouteDecision`（`route`、`tools`、`rationale`） |
| **L2b 图谱子图** | 已进入 `graphrag-query` / `text2sql-query` → 规划子任务、选 Cypher / SQL / LightRAG 等 | `PlannerOutput`、`tool_calls` 等 |

下文按 **L1 → 分支内提示 → L2a / L2b** 展开。

---

## 2. L1：`ROUTER_SYSTEM_PROMPT` 与 `analyze_and_route_query`

### 2.1 调用方式

- **位置**：`lg_builder.analyze_and_route_query`
- **系统提示**：`ROUTER_SYSTEM_PROMPT`（`lg_prompts.py`）
- **用户侧输入**：`[{"role": "system", "content": ROUTER_SYSTEM_PROMPT}] + state.messages`  
  即：**完整对话历史** 与路由提示一起送入模型，模型可结合上文消歧（但分类仍以「当前轮意图」为主）。
- **结构化输出**：`ChatOpenAI(..., tags=["router"]).with_structured_output(Router)`
- **温度**：`0.7`（与部分下游节点一致）

未配置 `OPENAI_API_KEY`（实际为 `settings` 中 LLM Key）时，路由节点直接抛错，不会进入 LLM。

### 2.2 `Router` 模型字段（`lg_states.Router`）

| 字段 | 含义 |
|------|------|
| `type` | **必填语义核心**，Literal 七种 + `text2sql-query`，须与 `route_query` 分支一致 |
| `logic` | 分类理由；会注入 `GENERAL_QUERY`、`GET_ADDITIONAL` 等系统提示的 `{logic}` |
| `question` | 规范化问句；缺省时实现里会用最后一条用户消息 |
| `decision` / `confidence` / `reasoning` | 可选扩展字段；主路由逻辑主要认 `type` |

`Router` 允许 `extra` 字段，便于兼容旧客户端；**条件边只依赖 `type`**（及后述 `configurable` 覆盖）。

### 2.3 `ROUTER_SYSTEM_PROMPT` 分类语义（与仓库文案一致）

以下为类型定义摘要，**修改请以 `lg_prompts.py` 原文为准**。

| `type` | 设计意图 | 典型用户表述 |
|--------|----------|----------------|
| `general-query` | 无需查内部知识库/库的轻量对话 | 问候、感谢、与菜谱无关的闲聊 |
| `additional-query` | 信息不足，应先追问 | 「想做菜」但无菜名/食材；营养问题缺份量；失败现象描述不清 |
| `kb-query` | **历史文化、长文本知识** | 典故、流派背景、地域文化、名人与菜等 |
| `graphrag-query` | **操作步骤、用量、技巧、图谱推理** | 怎么做、步骤、食材清单、火候、熟度判断、需从图谱/库综合的信息 |
| `text2sql-query` | **MySQL 统计/排名/聚合** | 多少、统计、总数、排名、TOP、占比、平均等 |
| `image-query` | 图片相关（识图或生图意图） | 结合上传图或明确要生成菜品图 |
| `file-query` | 用户上传文档类资料 | PDF/Excel/菜谱文档等 |

文末四条 **硬约束**（仓库内原文精神）：

1. 「有多少 / 统计 / 数量」→ `text2sql-query`
2. 「怎么做 / 需要什么食材」→ `graphrag-query`
3. 「历史 / 典故 / 文化背景」→ `kb-query`
4. 类型字符串须准确，勿夹杂其它 JSON 或多余字段（由结构化输出约束）

### 2.4 与 `route_query` 的映射

`route_query`（`lg_builder.py`）根据 `router.type` 返回 **下一节点名**（字符串）：

| `Router.type` | 下一节点 |
|---------------|----------|
| `general-query` | `respond_to_general_query` |
| `additional-query` | `get_additional_info` |
| `graphrag-query` 或 `text2sql-query` | `create_research_plan`（同一入口，子图内再分流 SQL/Cypher 等） |
| `image-query` | `create_image_query` |
| `file-query` | `create_file_query` |
| `kb-query` | `create_kb_query` |

**覆盖规则**：若 `state.config["configurable"]` 中存在 **`image_path`** 或 **`file_path`**，**无论 LLM 分类结果如何**，优先进入图片或文件节点。API 层传入附件路径时需知悉此行为。

### 2.5 启发式兜底 `_heuristic_router`

在 **LLM 调用异常** 或 **返回的 `type` 不在允许集合** 时启用；合法结构化输出**不会**再与启发式融合。

**关键词（小写匹配，中文按原样出现在 `question` 中）**：

- **倾向 `text2sql-query`**：`统计`、`多少`、`总数`、`数量`、`排名`
- **倾向 `graphrag-query`**：`怎么做`、`如何做`、`做法`、`步骤`、`火候`、`食材`、`原料`、`需要什么`、`配料`、`用什么`

若均不匹配且 LLM 失败，最终可落到默认 **`kb-query`**（`logic` 带 `fallback` 说明）。

## 3. L1 各分支：系统提示与占位符

以下常量均在 **`lg_prompts.py`**，由 `lg_builder` 各节点 `format` 或 `ChatPromptTemplate` 注入。

| 常量 | 占位符 / 注入 | 使用节点 | LLM `tags`（便于流式过滤） |
|------|----------------|----------|----------------------------|
| `GENERAL_QUERY_SYSTEM_PROMPT` | `{logic}` ← `router.logic` | `respond_to_general_query` | `general_query` |
| `GET_ADDITIONAL_SYSTEM_PROMPT` | `{logic}` ← `router.logic` | `get_additional_info`（通过护栏后） | `additional_info` |
| `GUARDRAILS_SYSTEM_PROMPT` | Human 模板拼接 `scope_description` + Neo4j schema | `get_additional_info` 前置护栏 | 同左模型 |
| `GET_IMAGE_SYSTEM_PROMPT` | `{image_description}` | 图片分支 | 视节点而定 |
| `RAGSEARCH_SYSTEM_PROMPT` | `{context}` | 检索后直接生成（若主图仍引用） | — |
| `GENERATE_QUERIES_SYSTEM_PROMPT` | 无 | 研究/查询生成相关路径 | — |
| `CHECK_HALLUCINATIONS` | `{documents}`、`{generation}` | 幻觉检测 | — |
| `IMAGE_GENERATION_ENHANCE_PROMPT` | `{user_query}` | 文生图扩写 | — |
| `IMAGE_GENERATION_SUCCESS_PROMPT` | `{dish_name}` | 文生图成功话术 | — |

### 3.1 `general-query` 分支：`GENERAL_QUERY_SYSTEM_PROMPT`

- 定位为 **下厨房风格客服**：称呼、emoji、拒答无关问题的四段式话术等。
- 系统段末尾有一段 **给「路由器」看的说明**（如强调做法类应选 `graphrag-query`）：用户**不会**看到，但可能让模型在 **已误入 general 分支** 时仍倾向自我纠正——**真正分支已由 L1 决定**，此处主要是文风与边界话术。
- 与 `GET_ADDITIONAL` 类似，文中要求追问「尽量 20 字以内」与 general 的长文指导并存，属 **提示词张力**；若需统一口径可一并改 `lg_prompts.py`。

### 3.2 `additional-query` 分支：护栏 + `GET_ADDITIONAL_SYSTEM_PROMPT`

1. **护栏链**：`GUARDRAILS_SYSTEM_PROMPT` + Human 消息，内容为  
   `scope_description`（内置菜谱助手业务范围长文）+ **Neo4j 图结构摘要**（`retrieve_and_parse_schema_from_graph_for_prompts`，连接失败则仅有 scope）。
2. **结构化输出**：`AdditionalGuardrailsOutput`，`decision` 为 **`end` | `proceed`**（见 `lg_builder`）。
3. **实现注意**：`GUARDRAILS_SYSTEM_PROMPT` 正文写的是输出 **`continue` / `end`**，与 Pydantic 字段 **`proceed` / `end`** 字面不一致；实际以 **`with_structured_output(AdditionalGuardrailsOutput)`** 及字段描述为准。后续若改提示词，建议 **统一文案与 schema**，减少模型混淆。
4. `decision == "end"`：固定中文拒答一句，不调用 `GET_ADDITIONAL`。
5. `decision == "proceed"`：用 `GET_ADDITIONAL_SYSTEM_PROMPT.format(logic=router.logic)` 生成 **单条追问**（文中亦限制尽量简短）。

## 4. L2a：知识库多工具子图（`kb-query` → `create_kb_multi_tool_workflow`）

主图 `create_kb_query` 编译的子图内，与「分类」直接相关的是 **三段提示**（均在 `multi_tool.py` 内联字符串，**非** `lg_prompts.py`）。

### 4.1 护栏 `guardrails_prompt`

- **角色**：企业知识库安全审查员。
- **默认业务范围**（可被 `scope_description` 参数覆盖）：仅 **历史渊源、命名、地域流派、典故、名人与菜**；明确 **不包含** 烹饪步骤、食材搭配建议；禁止违法、隐私、未授权主题。
- **结构化输出**：`KBGuardrailsDecision`（`decision='end'` 时带中文 `summary`）。

### 4.2 检索路由器 `router_prompt`

- **角色**：菜谱文化知识检索路由器。
- **要点**：**PostgreSQL（pgvector）优先**，Milvus 长文兜底；默认推荐 `tools: ['postgres', 'milvus']` 以走「先 PG 后有结果则停」的流程。
- **规则分档**：通用历史文化、仅结构化、明确要长篇叙事、外部/混合、超出范围（`tools: []`）。
- **Human 侧**：当前问题 + **最近若干轮对话**（`_history_to_text`，默认最多 4 条），用于指代消解。
- **输出**：`KBRouteDecision`：`route`（local / external / hybrid）、`tools`、`rationale`。

### 4.3 最终生成 `final_prompt`

- 依据 Milvus / PostgreSQL / 外部检索拼接的 context 作答；强调 **只讲文化、不讲做法**，信息不足时说明并建议换模块。

## 5. L2b：图谱多工具子图（`graphrag-query` / `text2sql-query` → `create_research_plan`）

进入 **`create_research_plan`** 后，使用 **`kg_sub_graph/prompts/kg_prompts.py`** 中多段提示（由 planner、tool_selection、text2cypher、summarize 等节点组合调用）。与 **主图 L1 路由** 的关系是：**L1 已承诺「走图谱/问数」**，此处负责 **拆解任务与选工具**。

| 常量 | 作用 |
|------|------|
| `GUARDRAILS_SYSTEM_PROMPT`（kg） | 图谱范围：输出 **`planner` / `end`**（与主图 `lg_prompts` 的护栏 **不是同一段**） |
| `PLANNER_SYSTEM_PROMPT` | 将用户问题拆成 **独立子任务**（配合 `planner/prompts.py` 中的人体规则段落） |
| `TOOL_SELECTION_SYSTEM_PROMPT` | 为子任务选工具：`cypher_query`、`predefined_cypher`、`text2sql_query`、LightRAG 等 |
| `TEXT2CYPHER_GENERATION_PROMPT` / `TEXT2CYPHER_VALIDATION_PROMPT` | Cypher 生成与审计 |
| `SUMMARIZE_SYSTEM_PROMPT` / `FINAL_ANSWER_SYSTEM_PROMPT` | 结果压缩与面向用户的终答风格 |

**工具选择节点**（`tool_selection/node.py`）另有 **代码层启发式**：`_looks_like_sql_question` 对 SQL 关键字、中英统计类词做检测，可与 LLM 工具选择叠加，排错时需结合日志。

## 6. L1 与 L2 的边界与常见冲突

1. **「统计」类问句**：L1 倾向 `text2sql-query`；进入研究计划后，工具选择提示也强调 **问数 / SQL**。若数据实际只在 Neo4j，可能出现路径拉扯，需用数据落库位置与测试用例校准。
2. **「历史」vs「做法」**：L1 用 `kb-query` vs `graphrag-query` 划分；若向量库已存全文做法，是否改走 `kb-query` 属 **产品策略**（见下文第 9 节草案）。
3. **主图 `image-query` vs configurable**：带 `image_path` 时 **强制** 图片节点，分类可能被覆盖。
4. **两处 GUARDRAILS**：`lg_prompts.GUARDRAILS_SYSTEM_PROMPT`（补充信息分支）与 `kg_prompts.GUARDRAILS_SYSTEM_PROMPT`（图谱子图）**文案与输出约定均不同**，修改时不要混贴。

---

## 7. 流式输出与 `tags`

主图路由与各节点 `ChatOpenAI` 使用不同 **`tags`**（如 `router`、`general_query`、`additional_info`），便于 **`astream` 时过滤事件**。改节点或复制节点时请保持 tag 语义清晰，避免前端订阅错流。

## 8. 调整提示词的操作流程

1. **备份**（可选）：复制 `lg_prompts.py` / `kg_prompts.py` / `multi_tool.py` 相关片段。
2. **编辑 `ROUTER_SYSTEM_PROMPT`**：保持 `type` 与 `Router` Literal **完全一致**；修改关键词导向时，同步评估 **`_heuristic_router`**，避免兜底与 LLM 新策略长期冲突。
3. **同步文档**：[智能体路由速查.md](智能体路由速查.md) 中的示例表若承诺具体行为，应一并更新。
4. **重启**：`docker compose restart backend` 或本地重启 uvicorn。
5. **验证**：
   - `python -m tests.test_agent_routing --single "红烧肉怎么做？"`（若项目提供）
   - `pytest tests/test_chat_api.py -v`  
   环境变量见 [环境变量与配置说明.md](环境变量与配置说明.md)。

## 9. 可选策略草案：「做法类优先 `kb-query`」

在 **确认 Milvus/pgvector 已覆盖菜谱全文**、且希望 **减少图谱/Cypher 压力** 时，可考虑调整 L1 提示与启发式，原则如下（需自行写成与现有章节 **无矛盾** 的完整系统提示）：

1. 以 **文本复述做法、步骤、食材清单** 为主 → 倾向 **`kb-query`**。
2. **明确多跳关系推理**（主料辅料关系、营养关联、复杂筛选）→ 保留 **`graphrag-query`**。
3. **`text2sql-query` / `general-query`** 边界不变。
4. 改后应用 **同一批问句** 对比 `router.type` 与端到端答案质量做回归。
