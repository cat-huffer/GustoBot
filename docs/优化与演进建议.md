# 优化与演进建议

本文从 **架构可靠性、数据一致性、检索与 RAG、Agent 编排、可观测性、安全、性能成本、工程化测试、产品能力** 等维度，列出 GustoBot **可考虑优化的点**与 **可新增的功能方向**。条目按 **影响面 / 实现成本** 大致标注，便于排期；**具体以当前仓库代码为准**，实施前请再 diff 一遍相关模块。

**相关基础文档**：[agent开发项目总览.md](agent开发项目总览.md)、[环境变量与配置说明.md](环境变量与配置说明.md)、[部署指南.md](部署指南.md)。

## 1. 架构与运行时可靠性

### 1.1 LangGraph Checkpoint：从内存到可横向扩展

**现状**：主图使用 **`MemorySaver`**，状态仅在 **单进程内存**；多副本部署时 **各实例状态不共享**，`thread_id` 无法跨 Pod 续聊。

**优化方向**：

- 换用 **持久化 Checkpointer**（如官方支持的 **PostgreSQL / Redis** 等实现，以 LangGraph 当前版本文档为准），使 **`thread_id`** 在 **多实例** 下一致。  
- 明确 **产品会话**（DB）与 **图状态**（checkpoint）的 **同步策略**：是否在每次 `ainvoke` 后 **裁剪/压缩 messages** 避免状态膨胀。

**收益**：水平扩展、重启不丢「当前会话上下文」（在可接受的产品定义内）。  
**成本**：中高（依赖运维、迁移、回归测试）。

### 1.2 `route_query` 与 `configurable`：行为显式化

**现状**：附件覆盖依赖 **`state.config`** 上是否有 **`configurable`**；与 LangGraph 版本、调用方式耦合，**初学者易踩坑**（见总览文档「常见坑」）。

**优化方向**：

- 在 **`RunnableConfig`** 文档化路径统一从 **`config` 参数**读取 `image_path`/`file_path`，或在 **节点内**显式注入 **`config: RunnableConfig`** 并传参，避免依赖 **`state.config`** 隐式存在。  
- 为 **`route_query`** 增加 **单测**：模拟带/不带附件的 `config`。

**收益**：减少环境差异导致的「本地能跑、线上不行」。  
**成本**：低到中。

### 1.3 图谱多工具：`error_tool_selection` 与边的完整性

**现状**：**`tool_selection`** 在无法选工具时可能 **`Command` 到 `error_tool_selection`**，而 **`create_multi_tool_workflow`** 的 **`add_node` 列表未必包含该节点**（曾见 **import `create_error_tool_selection_node` 但未注册** 的风险），极端路径下 **运行时报错**。

**优化方向**：

- **二选一**：要么 **注册 `error_tool_selection` 节点**并接到 **`summarize`/`final_answer`**；要么 **删除/改写** 该分支，统一回退到 **`final_answer` 带错误话术**。  
- 对 **`tool_selection` → 各工具节点** 的边做 **静态检查**（或集成测试）覆盖 **所有 `Command` 目标名**。

**收益**：消灭难以复现的线上崩溃。  
**成本**：低。

## 2. 数据与会话一致性

### 2.1 流式聊天：助手消息持久化（代码中已有 TODO）

**现状**：**`chat.py`** 流式路径注释写明：**流式场景下可能未把完整助手回复写入数据库**（存在 **`TODO 没有把 AI 助手回复写入数据库`** 类问题，以文件为准）。

**优化方向**：

- 在 **`stream_agent_response`** 结束或 **`done` 事件**时，**异步写入**助手消息（与同步 **`chat`** 路径对齐字段：`route`、`metadata`、必要时 `sources`）。  
- 注意 **流式分片拼接**：需在服务端 **缓冲全文** 再落库，或接受「仅存最终合并结果」。

**收益**：会话列表、审计、分析与 **非流式** 行为一致。  
**成本**：中（边界情况：客户端断开、超长回复）。

### 2.2 `agent_state` 与消息元数据策略

**现状**：持久化消息时 **过滤 `agent_state`**，避免体积过大；但排障时 **缺少完整图状态**。

**优化方向**：

- 可选 **异步写入对象存储 / 调试索引**（仅 debug 会话或采样），或 **结构化摘要**（路由类型、工具名、耗时）。  
- 定义 **保留时长与 GDPR/合规** 策略（若面向终端用户）。

**收益**：可观测与合规平衡。  
**成本**：中。

## 3. 检索、RAG 与回答质量

### 3.1 系统化 RAG 评估（当前以零散节点为主）

**现状**：无 **RAGAS / 黄金集** 一类流水线；仅有 **幻觉检测节点（未默认挂载）**、**终答校验**、**SQL/Cypher 校验** 等（见总览 **§10.10**）。

**优化方向**：

- 建立 **离线评测集**（问题、期望引用、可选标准答案），指标至少包含：**召回命中率、答案忠实度、路由准确率**。  
- 对 **`Router`**、**KB 路由**、**tool_selection** 做 **分模块回归**：改动提示词或关键词表时 **必跑**。  
- 将 **`check_hallucinations`** 以 **可配置开关** 接入主图或 **仅 KB/高风险分支**，并记录 **binary_score** 分布。

**收益**：迭代可量化，减少「凭感觉改提示词」。  
**成本**：中高（需标注与基建）。

### 3.2 重排与混合检索策略

**现状**：**`Reranker`** 与 **`KnowledgeService.search`** 已打通；KB 子图内 **PG 路径** 也有 rerank 分支。

**优化方向**：

- **A/B** 不同 **`RERANK_PROVIDER`** 与阈值，对比 **用户点赞/业务指标**（若有）。  
- 对 **hybrid** 场景显式定义：**向量分数 + BM25（若引入）** 的融合公式，避免仅靠 LLM 路由 **postgres/milvus**。

**收益**：难例召回与排序更稳。  
**成本**：中。

### 3.3 Query Transformation（查询改写）可选模块

**现状**：**Planner** 做 **任务分解**；无独立 **HyDE / 同义扩展** 模块（见总览 **§10.11**）；**`GENERATE_QUERIES_SYSTEM_PROMPT`** 在 **`lg_builder` 中曾出现仅 import、主路径未用** 的情况，易成死代码。

**优化方向**：

- 对 **短问、指代强** 的对话，在 **检索前** 增加 **「指代消解 + 独立检索句」** 节点（可用 **小模型** 降低成本）。  
- 要么 **删除未使用 import**，要么 **在 research/KB 节点显式使用** 多查询模板。

**收益**：多轮场景检索更准；代码更干净。  
**成本**：中。

## 4. Agent 编排、提示词与工具

### 4.1 护栏提示与 Schema 一致

**现状**：主图 **`get_additional_info`** 使用的 **`GUARDRAILS_SYSTEM_PROMPT`** 字面要求 **`continue/end`**，而结构化输出为 **`proceed/end`**，存在 **字面不一致**（总览与路由文档已提及）。

**优化方向**：**统一文案与 Pydantic 字段描述**，减少模型误解析。

**收益**：护栏稳定性提升。  
**成本**：低。

### 4.2 主图与图谱护栏「两套 GUARDRAILS」策略对齐

**现状**：**`lg_prompts.GUARDRAILS`** 与 **`kg_prompts.GUARDRAILS`** 目标不同，但用户体验上可能 **「主图放进来了、子图拒掉」** 或相反。

**优化方向**：梳理 **范围文案** 与 **拒答话术** 的 **产品一致性与优先级**（可在文档层定义 **L1/L2 护栏边界**）。

**收益**：减少用户困惑与投诉。  
**成本**：低（以产品与文案为主）。

### 4.3 工具与模型能力对齐

**优化方向**：

- **`bind_tools`** 的 schema **与真实工具参数** 严格同步（改字段必改 **`kg_tools_list`** 与执行节点）。  
- 对 **不支持 tool_calls 的模型**，提供 **纯 JSON 模式 fallback**（结构化输出 + 解析），避免单点模型切换导致全挂。

**收益**：可替换模型、降低供应商锁定风险。  
**成本**：中。

## 5. 可观测性：指标、追踪与日志

### 5.1 Prometheus（依赖已存在，业务未打点）

**现状**：**`requirements.txt`** 含 **`prometheus-client`**，业务代码 **未见 Counter/Histogram**（总览 **§10.13**）。

**优化方向**：

- 暴露 **`/metrics`**：**HTTP 状态码、chat 延迟直方图、按 `Router.type` 计数、子图失败率、外部依赖超时**。  
- **RED 方法** 或 **四大黄金信号** 选适合业务的子集即可。

**收益**：容量规划、告警、回归对比。  
**成本**：中。

### 5.2 LangSmith / OpenTelemetry 追踪

**现状**：未内置 LangSmith；**loguru** 应用日志为主。

**优化方向**：

- 启用 **LangChain/LangGraph 兼容的 tracing 环境变量**（按官方文档），或 **OTel** 接入 **Jaeger/Tempo**。  
- 为 **`thread_id`、`session_id`、路由类型** 注入 **trace attribute**，便于串联一次请求。

**收益**：跨节点排障时间显著下降。  
**成本**：中（密钥与采样率治理）。

### 5.3 结构化日志与敏感信息

**优化方向**：统一 **`service=`** 字段；**API Key、连接串** 禁止打日志；对 **用户问题** 可做 **采样或脱敏**（合规）。

**收益**：安全与可审计。  
**成本**：低。

## 6. 安全与合规

### 6.1 CORS 与 `CORS_ORIGINS`

**现状**：**`main.py`** 中 **`allow_origins=["*"]`**，与 **`settings.CORS_ORIGINS`** 可能 **不一致**（环境变量说明文档已提示）。

**优化方向**：生产环境 **收紧来源**，与前端实际域名一致；**开发/生产** 分配置。

**收益**：降低浏览器侧滥用风险。  
**成本**：低。

### 6.2 SQL / Cypher 注入与权限

**现状**：Text2SQL/Text2Cypher 强调 **校验与参数化**；仍需 **定期审计** 生成语句。

**优化方向**：**只读账号**、**表级权限**、**行级安全（若适用）**、**查询成本上限**（超时、LIMIT）。

**收益**：降低数据泄露与拖库风险。  
**成本**：中（与 DBA/运维协同）。

### 6.3 上传与文件路径

**优化方向**：**路径规范化** 防目录穿越；**病毒扫描 / 类型白名单**（若面向公网）；**大小限制** 与反向代理 **`client_max_body_size`** 对齐（部署文档已有相关思路）。

**收益**：减少滥用与 DoS。  
**成本**：中。

## 7. 性能与成本

### 7.1 模型调用次数与缓存

**优化方向**：

- **Redis 语义缓存**（`redis_cache.py` 已提供类）：在 **允许场景**下对 **embedding + 最终回复** 做缓存，降低 **重复热门问题** 成本。  
- **路由层小模型**：对 **极简单问候** 用规则或小模型，减少 **大模型路由** 调用。

**收益**：延迟与费用双降。  
**成本**：中（需防缓存污染与失效策略）。

### 7.2 子图并行与外部 IO

**现状**：**`Send`** 实现多任务并行 **tool_selection**；外部 Neo4j/Milvus/HTTP 仍可能 **阻塞**。

**优化方向**：**连接池**、**异步客户端**、**批量查询合并**、**合理超时与熔断**（避免拖垮事件循环）。

**收益**：高并发下更稳。  
**成本**：中到高。

### 7.3 向量索引与 Milvus

**优化方向**：按数据量调整 **索引类型、nprobe、分片**；**冷热分层**（若数据很大）。

**收益**：检索延迟与成本优化。  
**成本**：高（需 profiling）。

## 8. 工程化与测试

### 8.1 测试覆盖

**优化方向**：

- **路由单测**：`Router.type` 与 **`_heuristic_router`** 边界。  
- **子图集成测**：**mock LLM** 固定返回，验证 **边与工具选择**。  
- **回归集**：每次改 **`ROUTER_SYSTEM_PROMPT`** 跑一批问句。

**收益**：重构有信心。  
**成本**：中。

### 8.2 死代码与注释债

**优化方向**：清理 **未使用的 import**（如历史上 **仅 import 的提示常量**）、完善 **`lg_builder`** 中 **`TODO`** 注释所指逻辑或删除误导性 TODO。

**收益**：维护成本下降。  
**成本**：低。

### 8.3 类型与接口契约

**优化方向**：对 **`graph.ainvoke` 出入参**、**子图 `InputState`** 生成 **OpenAPI 或 TypedDict 严格校验**；减少 **`dict`/`Any`** 穿透。

**收益**：少踩运行时错误。  
**成本**：中。

## 9. 产品功能与体验（可演进方向）

| 方向 | 说明 |
|------|------|
| **多模态统一** | 图片/文件与文本路由 **策略产品化**（何时强制视觉链路、何时 OCR 后走 KB）。 |
| **用户反馈闭环** | 点赞/点踩 → 写入 **标注库** → 驱动 **评估集与模型/提示迭代**。 |
| **引用与可解释性** | KB 已部分支持 **`sources`**；可统一 **前端展示格式** 与 **图谱/SQL 路径的引用**。 |
| **多语言** | 路由与回答语言检测；检索 **跨语言 embedding** 或 **翻译节点**。 |
| **Admin 运维台** | 查看 **会话、路由分布、错误率**；**开关功能**（外搜、rerank）无需改代码。 |

## 10. 优先级建议（仅供参考）

| 优先级 | 项 | 理由 |
|--------|-----|------|
| **P0** | 流式助手消息落库、**error_tool_selection 边完整性** | 数据一致性与稳定性 |
| **P1** | **持久化 checkpoint**（若要多副本）、Prometheus 基础指标、CORS 生产收紧 | 可扩展与安全基线 |
| **P2** | RAG 离线评测集、护栏文案与 Schema 对齐、Query 改写试点 | 质量与可迭代性 |
| **P3** | LangSmith/OTel、Redis 缓存接入主路径、高级索引 | 成本与排障体验 |
