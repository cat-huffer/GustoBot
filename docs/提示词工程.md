# 提示词工程与路由分类说明

本文系统说明 **主 LangGraph**（`lg_builder`）中的 **意图路由**、各分支 **应答提示词**，以及 **知识库子图**、**图谱多工具子图** 内与「分类 / 规划 / 选工具」相关的提示词；并从**初学者**角度归纳：**在本仓库里改提示词一般要怎么做、要和哪些代码一起核对、常见坑是什么**。修改路由或分类行为时，请与此文、[智能体路由速查.md](智能体路由速查.md)、测试用例及源码对照。

**权威源码**：

- 主图提示词常量：`gustobot/application/agents/lg_prompts.py`
- 主图编排与路由逻辑：`gustobot/application/agents/lg_builder.py`
- 路由结构化类型：`gustobot/application/agents/lg_states.py` → `Router`
- 图谱侧提示词：`gustobot/application/agents/kg_sub_graph/prompts/kg_prompts.py`
- KB 多工具内嵌提示：`gustobot/application/agents/kg_sub_graph/agentic_rag_agents/workflows/multi_agent/multi_tool.py`
- 搜索与 KB 工具提示：`gustobot/application/prompts/search_prompts.py`、`gustobot/application/agents/kb_tools/prompts.py`
- 联网搜索编排（消费 `search_prompts`）：`gustobot/application/services/search_service.py`
- 图谱侧工具 schema 文案：`gustobot/application/agents/kg_sub_graph/kg_tools_list.py`（与 `TOOL_SELECTION_SYSTEM_PROMPT` 叠加）

**提示词工程总览**（源文件地图、编排模式、与代码协同）：见本文 **第 10 节**。**初学者建议先读第 0 节（含 0.5～0.7）与第 11 节（注意事项）**，再按需深入第 2～5 节。与检索链路的对应关系见 [RAG.md](RAG.md)、主图与子图边见 [workflow工作流.md](workflow工作流.md)。

## 0. 文档导读与心智模型（初学者）

### 0.1 提示词在这里到底干什么？

在本项目里，「提示词」大多是 **`system` 角色的大段中文说明**，告诉模型：**你是谁、能做什么、不能做什么、输出要长成什么样**。它们不单独运行，而是和 **用户消息 / 对话历史 / 检索到的上下文** 一起送给 LLM。

可以粗略分成三类用途：

1. **分类 / 决策**：例如 L1 路由要把用户问题标成 `kb-query` 还是 `graphrag-query`。这类往往配合 **`with_structured_output(Pydantic)`**，强制输出合法字段，减少模型瞎编 JSON。  
2. **生成答案**：例如 `general-query` 分支的客服口吻、`kb_tools` 里基于检索片段写回答。这类更依赖 **文风、禁令（不胡编）、引用格式**。  
3. **中间步骤**：例如 Text2Cypher、SQL 生成、汇总、终答——每一段提示只负责流水线中的一环，**前后节点还会用代码校验、重试、换工具**。

**重要**：提示词不是「唯一真理」。**条件边、启发式关键词、`configurable` 强制附件路径** 都会改变实际走向；改文案时务必把 **代码里与提示词平行的逻辑** 一起想一遍（见第 10.4 节）。

### 0.2 为什么有好几层「路由」？

- **L1（主图）**：先决定走哪条「主干道」（闲聊 / 追问 / 向量知识库 / 图谱+问数 / 图 / 文件等）。走错这里，后面子图再强也救不回来。  
- **L2a（KB 子图）**：已经在「历史文化类知识库」通道里，再细分用 PostgreSQL、Milvus、外搜等。  
- **L2b（图谱子图）**：已经在「做法/图谱/问数」通道里，再规划子任务、选 Cypher / SQL / LightRAG 等。

分层的目的：**缩小每一步模型的决策空间**，并让不同团队/模块可以独立改提示而不把整个主图拖垮。

### 0.3 改提示词时最容易忽略的三件事

1. **Pydantic / Literal 与文案一致**：提示里写 `continue`，若 schema 里是 `proceed`，模型再听话也会乱（见第 3.2 节）。  
2. **双份提示**：同名 `GUARDRAILS`、Cypher 在 `kg_prompts` 与 `cypher_tools/prompts.py` 各有一份时，要确认 **运行时到底加载哪条链**（见第 10.5 节）。  
3. **工具描述 `Field(description)`**：`TOOL_SELECTION` 的 system 段与 `kg_tools_list` 里工具类的描述 **叠加** 给模型看，只改一边可能不够。

### 0.4 建议阅读顺序

1. **§0.5～0.7**（本页）：先建立「怎么改、注意什么」的预期。  
2. 第 1 节：三层路由对照表。  
3. 第 2～3 节：主图 L1 + 各分支常量。  
4. 第 11 节：注意事项、自查表与 **§11.0 改前清单**。  
5. 第 4～5 节：KB / 图谱子图提示。  
6. 第 10 节：工程化组织方式；第 12 节：需要时对源码片段。

### 0.5 提示词工程一般要怎么做？（可落地的流程）

「提示词工程」在这里不是玄学，而是：**用自然语言写清规则，再和代码、Schema、测试绑在一起迭代**。建议按下面顺序动手（与第 8、10.7 节互补）：

1. **先定目标**：要解决的是「路由分错类」「护栏误杀」「终答口吻」「少胡编」里的哪一类？一次只动一条线，避免一改一大段导致无法归因。  
2. **找到权威源文件**：主图大段在 `lg_prompts.py`；图谱在 `kg_prompts.py` 与各组件 `prompts.py`；KB 多工具在 `multi_tool.py` 内联（见 **§10.2**）。**改之前用全文搜索**确认没有第二份同名/同职责文案（见 **§10.5**）。  
3. **写 / 改 system 时写清四件事**（见 **§0.6**）：**角色与边界**、**输入输出约定**、**禁止项**、**与 Pydantic/Literal 一致的字段名**（若有结构化输出）。  
4. **对照代码里的「平行逻辑」**：条件边、启发式关键词、`configurable` 覆盖、工具 `Field(description)`——只改提示可能**完全无效**（见 **§0.7**、**§10.4**）。  
5. **小步试跑**：用少量固定问句（可与 **§11.6 自查表** 现象对应）看 `router.type`、护栏 `decision`、工具选择是否符合预期；再跑相关 `pytest` / 手工调 API。  
6. **记录与回归**：提示大改时建议在提交说明里写清「动了哪条链、期望行为变化」，便于以后排查「为什么线上和文档不一致」。

### 0.6 写好系统提示，初学者最该盯住的要点

| 要点 | 说明 |
|------|------|
| **一条提示一件事** | 路由提示专注「分类」；生成提示专注「怎么说」；不要把「分类规则」和「客服口吻」混成一大段，否则模型容易抓错重点。 |
| **结构化输出时，字面值要跟 Schema 对齐** | 例如护栏里若 Pydantic 是 `proceed` / `end`，提示里就不要再写 `continue` / `end` 混用（见 **§3.2**）。 |
| **类型名与代码 Literal 完全一致** | `Router.type` 的取值必须落在 `allowed_types` 与 `lg_states.Router` 的 Literal 里；多一个空格、大小写不对都会进 fallback（见 **§2.6**）。 |
| **占位符名别手滑** | `{logic}`、`{context}` 等与 `lg_builder` 里 `.format` 一致；改占位符必须同步改注入代码（见 **§10.5**）。 |
| **别假设「模型会看完全文」** | 会话很长时，路由把**整段历史**塞进模型（见 **§2.1**），早期轮次可能干扰当前意图；这是**提示词之外**要治理的点（第 13 节）。 |
| **温度不是全图统一** | 路由、KB 子图、Text2SQL 各节点可能不同 `temperature`（**§10.6**）；排错时别只怪文案。 |
| **工具描述双源** | `TOOL_SELECTION` 的 system 与 `kg_tools_list` 里 `Field(description)` **叠加**；只改一边可能不够（**§0.3**）。 |

### 0.7 只改提示不够：必须和代码一起想的情况（初学者易忽略）

下面这些情况，**光润色 `ROUTER_SYSTEM_PROMPT` 或工具选择文案，行为可能不变**：

- **合法结构化路由不会再走启发式**：LLM 正常返回且 `type` 合法时，**不会**再与 `_heuristic_router` 合并（**§2.5**）。线上若仍像「关键词路由」，先查是否 **LLM 失败**或 **非法 type**。  
- **图谱工具选择前的代码短路**：`_looks_like_sql_question` + `route_type`、**`DESCRIPTIVE_KEYWORDS`** 等 **先于** `bind_tools`（**§5**）。  
- **附件覆盖路由**：`image_path` / `file_path` 存在时 **强制**进图片/文件节点（**§2.4**）。  
- **KB 子图内外搜开关**：模型选了 `external`/`hybrid` 也可能被代码压成 `local`（**§4.2**）。  
- **主图未挂载的常量**：如 `RAGSEARCH_SYSTEM_PROMPT` 等**未 `add_node`** 时，改字也不影响默认对话（**§3**、**§11.1**）。

**结论**：改提示词时，打开对应的 **`lg_builder` / 子图节点 / `multi_tool.py`**，看一遍「提示之后还有什么 if」，再下结论。

## 1. 概念分层：三层「路由」不要混用

| 层级 | 作用 | 典型输出 |
|------|------|----------|
| **L1 主路由** | 用户一句问话 → 主图六大分支之一 | `Router.type`（如 `kb-query`、`graphrag-query`） |
| **L2a KB 子路由** | 已进入 `kb-query` → 选 postgres / milvus / 外搜等 | `KBRouteDecision`（`route`、`tools`、`rationale`） |
| **L2b 图谱子图** | 已进入 `graphrag-query` / `text2sql-query` → 规划子任务、选 Cypher / SQL / LightRAG 等 | `PlannerOutput`、`tool_calls` 等 |

## 2. L1：`ROUTER_SYSTEM_PROMPT` 与 `analyze_and_route_query`

### 2.1 调用方式

- **位置**：`lg_builder.analyze_and_route_query`
- **系统提示**：`ROUTER_SYSTEM_PROMPT`（`lg_prompts.py`）
- **用户侧输入**：`[{"role": "system", "content": ROUTER_SYSTEM_PROMPT}] + state.messages`  
  即：**完整对话历史** 与路由提示一起送入模型，模型可结合上文消歧（但分类仍以「当前轮意图」为主）。
- **结构化输出**：`ChatOpenAI(..., tags=["router"]).with_structured_output(Router)`
- **温度**：`0.7`（与部分下游节点一致）

未配置 `OPENAI_API_KEY` 时，路由节点 **`RuntimeError`**，不会进入 LLM（与 `lg_builder` 中校验字段一致；若部署使用 `LLM_API_KEY` 等别名，需保证最终写入 `settings.OPENAI_API_KEY` 或同步修改校验逻辑）。

**初学者注意（上下文长度）**：路由把 **`state.messages` 全量**拼在 system 后面。会话很长时，会更快触达模型 **上下文上限**、增加延迟与费用，且早期消息可能把「当前意图」冲淡。若线上出现路由不稳定，可考虑在代码侧对路由输入做 **截断/摘要**（当前实现未默认裁剪，属潜在优化点，见第 13 节）。

**合法输出不再融合启发式**：`with_structured_output(Router)` 成功且 `type ∈ allowed_types` 时，**不会**与 `_heuristic_router` 结果合并；启发式仅用于 **LLM 异常**或 **非法 `type`** 分支（见第 12.2 节摘录）。

### 2.2 `Router` 模型字段（`lg_states.Router`）

| 字段 | 含义 |
|------|------|
| `type` | **必填语义核心**，Literal 七种 + `text2sql-query`，须与 `route_query` 分支一致 |
| `logic` | 分类理由；会注入 `GENERAL_QUERY`、`GET_ADDITIONAL` 等系统提示的 `{logic}` |
| `question` | 规范化问句；缺省时实现里会用最后一条用户消息 |
| `decision` / `confidence` / `reasoning` | 可选扩展字段；主路由逻辑主要认 `type` |

`Router` 允许 `extra` 字段，便于兼容旧客户端；**条件边只依赖 `type`**（及后述 `configurable` 覆盖）。

### 2.3 `ROUTER_SYSTEM_PROMPT` 分类语义（与仓库文案一致）

以下为类型定义摘要，**修改请以 `lg_prompts.py` 原文为准**。

| `type` | 设计意图 | 典型用户表述 |
|--------|----------|----------------|
| `general-query` | 无需查内部知识库/库的轻量对话 | 问候、感谢、与菜谱无关的闲聊 |
| `additional-query` | 信息不足，应先追问 | 「想做菜」但无菜名/食材；营养问题缺份量；失败现象描述不清 |
| `kb-query` | **历史文化、长文本知识** | 典故、流派背景、地域文化、名人与菜等 |
| `graphrag-query` | **操作步骤、用量、技巧、图谱推理** | 怎么做、步骤、食材清单、火候、熟度判断、需从图谱/库综合的信息 |
| `text2sql-query` | **MySQL 统计/排名/聚合** | 多少、统计、总数、排名、TOP、占比、平均等 |
| `image-query` | 图片相关（识图或生图意图） | 结合上传图或明确要生成菜品图 |
| `file-query` | 用户上传文档类资料 | PDF/Excel/菜谱文档等 |

文末四条 **硬约束**（仓库内原文精神）：

1. 「有多少 / 统计 / 数量」→ `text2sql-query`
2. 「怎么做 / 需要什么食材」→ `graphrag-query`
3. 「历史 / 典故 / 文化背景」→ `kb-query`
4. 类型字符串须准确，勿夹杂其它 JSON 或多余字段（由结构化输出约束）

### 2.4 与 `route_query` 的映射

`route_query`（`lg_builder.py`）根据 `router.type` 返回 **下一节点名**（字符串）：

| `Router.type` | 下一节点 |
|---------------|----------|
| `general-query` | `respond_to_general_query` |
| `additional-query` | `get_additional_info` |
| `graphrag-query` 或 `text2sql-query` | `create_research_plan`（同一入口，子图内再分流 SQL/Cypher 等） |
| `image-query` | `create_image_query` |
| `file-query` | `create_file_query` |
| `kb-query` | `create_kb_query` |

**覆盖规则**：若 `state.config["configurable"]` 中存在 **`image_path`** 或 **`file_path`**，**无论 LLM 分类结果如何**，优先进入图片或文件节点。API 层传入附件路径时需知悉此行为。

### 2.5 启发式兜底 `_heuristic_router`

在 **LLM 调用异常** 或 **返回的 `type` 不在允许集合** 时启用；合法结构化输出**不会**再与启发式融合。

**关键词（小写匹配，中文按原样出现在 `question` 中）**：

- **倾向 `text2sql-query`**：`统计`、`多少`、`总数`、`数量`、`排名`
- **倾向 `graphrag-query`**：`怎么做`、`如何做`、`做法`、`步骤`、`火候`、`食材`、`原料`、`需要什么`、`配料`、`用什么`

若均不匹配且 LLM 失败，最终可落到默认 **`kb-query`**（`logic` 带 `fallback` 说明）。

### 2.6 非法 `type` 时的回退顺序（与提示词并列记忆）

当模型返回的 `type` **不在** `allowed_types` 时：

1. 若 **`_heuristic_router(question_text)` 非空**：采用该启发式 `Router`，并把 LLM 的 `logic` 写入（若为空则补全）。  
2. 否则：固定 **`kb-query`**，`logic` 为 `fallback: invalid router output` 或原 `logic`。

因此：**改宽 `ROUTER_SYSTEM_PROMPT` 里的类型描述时，必须同步扩展 `allowed_types`**，否则新类型会被当成非法而落到上述回退，表现为「明明模型想分新类，却进了 kb 或关键词类」。

### 2.7 `create_research_plan` 传入子图的 `route_type`

`create_research_plan` 将主图 **`state.router.type`**（`graphrag-query` 或 `text2sql-query`）写入子图输入 **`route_type`**，经 planner 状态传到 **`tool_selection`**。工具选择节点中 **`_looks_like_sql_question` 且 `route_type == "text2sql-query"`** 时会 **短路** 到 Text2SQL，**先于** `bind_tools` 链执行——仅改 `TOOL_SELECTION_SYSTEM_PROMPT` 无法覆盖该路径。

## 3. L1 各分支：系统提示与占位符

以下常量均在 **`lg_prompts.py`**，由 `lg_builder` 各节点 `format` 或 `ChatPromptTemplate` 注入。

| 常量 | 占位符 / 注入 | 使用节点 | LLM `tags`（便于流式过滤） |
|------|----------------|----------|----------------------------|
| `GENERAL_QUERY_SYSTEM_PROMPT` | `{logic}` ← `router.logic` | `respond_to_general_query` | `general_query` |
| `GET_ADDITIONAL_SYSTEM_PROMPT` | `{logic}` ← `router.logic` | `get_additional_info`（通过护栏后） | `additional_info` |
| `GUARDRAILS_SYSTEM_PROMPT` | Human 模板拼接 `scope_description` + Neo4j schema | `get_additional_info` 前置护栏 | 同左模型 |
| `GET_IMAGE_SYSTEM_PROMPT` | `{image_description}` | 图片分支 | 视节点而定 |
| `RAGSEARCH_SYSTEM_PROMPT` | `{context}` | **当前主编译图未挂载**：`lg_builder` 仅 import，无节点调用；若要做「纯 RAG + 该模板」需自行 `add_node` | — |
| `GENERATE_QUERIES_SYSTEM_PROMPT` | 无 | **同上**，属预留/文档约定，主路径未接 | — |
| `CHECK_HALLUCINATIONS` | `{documents}`、`{generation}` | 函数 `check_hallucinations` 已定义，但 **未** `builder.add_node` 进主图；供子图扩展或手工编排 | `hallucinations`（若接入） |
| `IMAGE_GENERATION_ENHANCE_PROMPT` | `{user_query}` | 文生图扩写 | — |
| `IMAGE_GENERATION_SUCCESS_PROMPT` | `{dish_name}` | 文生图成功话术 | — |

### 3.1 `general-query` 分支：`GENERAL_QUERY_SYSTEM_PROMPT`

- 定位为 **下厨房风格客服**：称呼、emoji、拒答无关问题的四段式话术等。
- 系统段末尾有一段 **给「路由器」看的说明**（如强调做法类应选 `graphrag-query`）：用户**不会**看到，但可能让模型在 **已误入 general 分支** 时仍倾向自我纠正——**真正分支已由 L1 决定**，此处主要是文风与边界话术。
- 与 `GET_ADDITIONAL` 类似，文中要求追问「尽量 20 字以内」与 general 的长文指导并存，属 **提示词张力**；若需统一口径可一并改 `lg_prompts.py`。

### 3.2 `additional-query` 分支：护栏 + `GET_ADDITIONAL_SYSTEM_PROMPT`

1. **护栏链**：`GUARDRAILS_SYSTEM_PROMPT` + Human 消息，内容为  
   `scope_description`（内置菜谱助手业务范围长文）+ **Neo4j 图结构摘要**（`retrieve_and_parse_schema_from_graph_for_prompts`，连接失败则仅有 scope）。
2. **结构化输出**：`AdditionalGuardrailsOutput`，`decision` 为 **`end` | `proceed`**（见 `lg_builder`）。
3. **实现注意**：`GUARDRAILS_SYSTEM_PROMPT` 正文写的是输出 **`continue` / `end`**，与 Pydantic 字段 **`proceed` / `end`** 字面不一致；实际以 **`with_structured_output(AdditionalGuardrailsOutput)`** 及字段描述为准。后续若改提示词，建议 **统一文案与 schema**，减少模型混淆。
4. `decision == "end"`：固定中文拒答一句，不调用 `GET_ADDITIONAL`。
5. `decision == "proceed"`：用 `GET_ADDITIONAL_SYSTEM_PROMPT.format(logic=router.logic)` 生成 **单条追问**（文中亦限制尽量简短）。

### 3.3 `image-query` 分支

- **识图/描述类**：`GET_IMAGE_SYSTEM_PROMPT.format(image_description=...)` + `ChatOpenAI`（`lg_builder.create_image_query`），将视觉模型产出的描述与用户问题一并约束。  
- **文生图子路径**：`IMAGE_GENERATION_ENHANCE_PROMPT` 扩写 prompt → 调用图片生成 HTTP API → `IMAGE_GENERATION_SUCCESS_PROMPT` 拼成功回复；依赖 `IMAGE_GENERATION_*` 配置，与向量/图谱提示词无关。

### 3.4 `file-query` 分支（几乎不用 `lg_prompts`）

- Excel：走摄取服务 HTTP，**固定中文状态句**（无 LLM 提示词模板）。  
- 文本类入库后：调用 **`create_knowledge_query_node`**，系统提示来自 **`kb_tools/prompts.build_knowledge_system_prompt`**（见第 12.4 节），**不是** `RAGSEARCH_SYSTEM_PROMPT`。

### 3.5 联网搜索服务与 `search_prompts.py`

`SearchService`（`application/services/search_service.py`）使用：

- **`SEARCH_SYSTEM_PROMPT`**：`{tools_description}` 注入工具说明，驱动「何时调用检索工具」的 system 行为。  
- **`SEARCH_SUMMARY_PROMPT`**：`{context}`、`{cur_date}`、`{query}`，把网页片段格式化为可总结上下文。

与 **`kb_tools`** 里直接 `SearchTool` + 自建上下文的用法 **并列存在**；改「外搜话术」时要分清走的是 **search_service 链** 还是 **KB 节点内联拼接**。

### 3.6 `kb-query` 主路径上的 LLM 参数（`create_kb_query`）

子工作流内用于护栏/路由/合成的 `ChatOpenAI`：**`temperature=0.3`**，**`tags=["kb_multi_tool"]`**。`configurable` 可覆盖 **`kb_top_k`**、**`kb_similarity_threshold`**、**`kb_filter_expr`**（不改变提示词文件，但改变检索进 `final_prompt` 的料）。回退到 `create_knowledge_query_node` 时仍用 `kb_tools` 的 system 模板。

## 4. L2a：知识库多工具子图（`kb-query` → `create_kb_multi_tool_workflow`）

主图 `create_kb_query` 编译的子图内，与「分类」直接相关的是 **三段提示**（均在 `multi_tool.py` 内联字符串，**非** `lg_prompts.py`）。

### 4.1 护栏 `guardrails_prompt`

- **角色**：企业知识库安全审查员。
- **默认业务范围**（可被 `scope_description` 参数覆盖）：仅 **历史渊源、命名、地域流派、典故、名人与菜**；明确 **不包含** 烹饪步骤、食材搭配建议；禁止违法、隐私、未授权主题。
- **结构化输出**：`KBGuardrailsDecision`（`decision='end'` 时带中文 `summary`）。

### 4.2 检索路由器 `router_prompt`

- **角色**：菜谱文化知识检索路由器。
- **要点**：**PostgreSQL（pgvector）优先**，Milvus 长文兜底；默认推荐 `tools: ['postgres', 'milvus']` 以走「先 PG 后有结果则停」的流程。
- **规则分档**：通用历史文化、仅结构化、明确要长篇叙事、外部/混合、超出范围（`tools: []`）。
- **Human 侧**：当前问题 + **最近若干轮对话**（`_history_to_text(history, limit=4)`），用于指代消解。
- **输出**：`KBRouteDecision`：`route`（local / external / hybrid）、`tools`、`rationale`。
- **与外搜开关**：若模型给出 `external`/`hybrid` 但配置关闭外搜，代码会把 `route` 压成 **`local`**（见 `multi_tool.py` 中 router 节点），提示词里「可外搜」的句子可能被运行时策略覆盖。

### 4.3 最终生成 `final_prompt`

- 依据 Milvus / PostgreSQL / 外部检索拼接的 context 作答；强调 **只讲文化、不讲做法**，信息不足时说明并建议换模块。
- **与 `kb_tools` 的差异**：`kb_tools` 面向「菜谱助手 + 步骤可列」；KB 子图 `final_prompt` 刻意 **压制做法类输出**，同一 Milvus 数据在两个入口下 **话术约束相反**，改提示时勿混用两段模板。

### 4.4 `scope_description` 与默认业务范围

`create_kb_multi_tool_workflow(..., scope_description=...)` 可覆盖护栏默认文案；未传入时使用 `multi_tool.py` 内 **长段默认 scope**（历史文化、禁止做法与敏感域）。与主图 `create_research_plan` 里为图谱写的 **`scope_description`** **不是同一段文字**，分别服务 KB 子图护栏与图谱多工具护栏。

## 5. L2b：图谱多工具子图（`graphrag-query` / `text2sql-query` → `create_research_plan`）

进入 **`create_research_plan`** 后，使用 **`kg_sub_graph/prompts/kg_prompts.py`** 中多段提示（由 planner、tool_selection、text2cypher、summarize 等节点组合调用）。与 **主图 L1 路由** 的关系是：**L1 已承诺「走图谱/问数」**，此处负责 **拆解任务与选工具**。

| 常量 | 作用 |
|------|------|
| `GUARDRAILS_SYSTEM_PROMPT`（kg） | 图谱范围：输出 **`planner` / `end`**（与主图 `lg_prompts` 的护栏 **不是同一段**） |
| `PLANNER_SYSTEM_PROMPT` | 将用户问题拆成 **独立子任务**（配合 `planner/prompts.py` 中的人体规则段落） |
| `TOOL_SELECTION_SYSTEM_PROMPT` | 为子任务选工具：`cypher_query`、`predefined_cypher`、`text2sql_query`、LightRAG 等 |
| `TEXT2CYPHER_GENERATION_PROMPT` / `TEXT2CYPHER_VALIDATION_PROMPT` | Cypher 生成与审计 |
| `SUMMARIZE_SYSTEM_PROMPT` / `FINAL_ANSWER_SYSTEM_PROMPT` | 结果压缩与面向用户的终答风格 |

**`PROMPT_MAPPING`（`kg_prompts.py` 文末）** 当前仅含：`planner`、`guardrails`、`text2cypher_generation`、`text2cypher_validation`、`summarize`、`final_answer`（**无** `tool_selection` 键）。工具选择依赖 **`tool_selection/prompts.py`** 直接 import **`TOOL_SELECTION_SYSTEM_PROMPT`**，勿误以为能从 `PROMPT_MAPPING["tool_selection"]` 取到。

**`kg_prompts` 全文摘要（便于检索，修改以源码为准）**：

- **GUARDRAILS（图谱）**：仅允许输出 **`planner`** 或 **`end`**（与主图补充信息护栏的 **`proceed`/`end`** 完全不同）。  
- **PLANNER**：拆子任务，示例为中文菜谱场景。  
- **TEXT2CYPHER_GENERATION**：图谱标签/关系清单 + 参数化 Cypher 规则。  
- **TEXT2CYPHER_VALIDATION**：安全、语法、性能审计要点。  
- **TOOL_SELECTION**：四工具分工（动态 Cypher / 预定义 / Text2SQL / LightRAG）。  
- **SUMMARIZE / FINAL_ANSWER**：亲切口吻、步骤顺序、空结果话术、终答结构。

**工具选择模板结构**（`create_tool_selection_prompt_template`）：**system** = `TOOL_SELECTION_SYSTEM_PROMPT`，**human** = `Question: {question}`；子任务文本来自 planner 的 `Send`，**不含**完整对话历史（与 L1 路由不同）。

**工具选择节点**（`tool_selection/node.py`）另有 **代码层启发式**（先于 `bind_tools`）：

| 规则 | 条件 | 跳转 |
|------|------|------|
| 描述类关键词 | `DESCRIPTIVE_KEYWORDS` 命中（如口味、营养、功效、食材、材料…） | `customer_tools` / GraphRAG |
| SQL 倾向 | `_looks_like_sql_question` 且 `route_type == "text2sql-query"` | `text2sql_query` |
| 默认 | LLM `bind_tools` + `PydanticToolsParser(first_tool_only=True)` | 各工具或 `cypher_query` 回退 |

**SQL_KEYWORDS / SQL_PATTERN** 与 `_looks_like_sql_question` 定义在同一文件，改 L1「问数」或工具选择行为时需与 **`ROUTER_SYSTEM_PROMPT`**、**`TOOL_SELECTION_SYSTEM_PROMPT`** 一并回归。

## 6. L1 与 L2 的边界与常见冲突

1. **「统计」类问句**：L1 倾向 `text2sql-query`；进入研究计划后，工具选择提示也强调 **问数 / SQL**。若数据实际只在 Neo4j，可能出现路径拉扯，需用数据落库位置与测试用例校准。
2. **「历史」vs「做法」**：L1 用 `kb-query` vs `graphrag-query` 划分；若向量库已存全文做法，是否改走 `kb-query` 属 **产品策略**（见下文第 9 节草案）。
3. **主图 `image-query` vs configurable**：带 `image_path` 时 **强制** 图片节点，分类可能被覆盖。
4. **两处 GUARDRAILS**：`lg_prompts.GUARDRAILS_SYSTEM_PROMPT`（补充信息分支）与 `kg_prompts.GUARDRAILS_SYSTEM_PROMPT`（图谱子图）**文案与输出约定均不同**，修改时不要混贴。

## 7. 流式输出与 `tags`

主图路由与各节点 `ChatOpenAI` 使用不同 **`tags`**（如 `router`、`general_query`、`additional_info`），便于 **`astream` 时过滤事件**。改节点或复制节点时请保持 tag 语义清晰，避免前端订阅错流。

## 8. 调整提示词的操作流程

与 **§0.5** 的六步流程一致，此处写得更「操作手册」向：

1. **备份**（可选）：复制 `lg_prompts.py` / `kg_prompts.py` / `multi_tool.py` 相关片段。
2. **编辑 `ROUTER_SYSTEM_PROMPT`（或目标常量）**：保持 `type` 与 `Router` Literal **完全一致**；修改关键词导向时，同步评估 **`_heuristic_router`**，避免兜底与 LLM 新策略长期冲突。
3. **跑一遍 §11.0 检查清单**：尤其结构化字段与双源提示。
4. **同步文档**：[智能体路由速查.md](智能体路由速查.md) 中的示例表若承诺具体行为，应一并更新。
5. **重启**：`docker compose restart backend` 或本地重启 uvicorn（提示在进程内加载，**热重载未必覆盖已 import 的常量**，以实际运行为准）。
6. **验证**：
   - `python -m tests.test_agent_routing --single "红烧肉怎么做？"`（若项目提供）
   - `pytest tests/test_chat_api.py -v`  
   环境变量见 [环境变量与配置说明.md](环境变量与配置说明.md)。

## 9. 可选策略草案：「做法类优先 `kb-query`」

在 **确认 Milvus/pgvector 已覆盖菜谱全文**、且希望 **减少图谱/Cypher 压力** 时，可考虑调整 L1 提示与启发式，原则如下（需自行写成与现有章节 **无矛盾** 的完整系统提示）：

1. 以 **文本复述做法、步骤、食材清单** 为主 → 倾向 **`kb-query`**。
2. **明确多跳关系推理**（主料辅料关系、营养关联、复杂筛选）→ 保留 **`graphrag-query`**。
3. **`text2sql-query` / `general-query`** 边界不变。
4. 改后应用 **同一批问句** 对比 `router.type` 与端到端答案质量做回归。

## 10. 提示词工程（本项目如何组织与使用提示词）

本节从**工程视角**说明：提示词存在哪里、如何与 LangChain/LangGraph 拼接、和结构化输出/代码规则如何配合，便于你改文案时不踩坑。前文第 2～5 节是**按路由链路**写的「行为说明」，本节是**横向切面**。

### 10.1 工程目标

- **可维护**：主对话、图谱子图、知识库子图、搜索服务各自有清晰归属，避免「同一意图多份互相打架的 system 段」。
- **可观测**：关键节点为 `ChatOpenAI` 打 **`tags`**，流式过滤与日志可对齐到「是哪一段提示在说话」。
- **可约束**：路由、护栏、工具选择等优先 **`with_structured_output(Pydantic)`**，减少自由文本跑偏；生成类（Cypher/SQL/总结）再用长 system 描述领域与格式。

### 10.2 源文件地图（按包归类）

| 位置 | 内容形态 | 主要职责 |
|------|----------|----------|
| `gustobot/application/agents/lg_prompts.py` | **大段字符串常量** | 主图：L1 路由、general/additional、补充信息护栏、RAG、幻觉检测、文生图等；顶部 docstring 列出常量与占位符对照。 |
| `gustobot/application/agents/kg_sub_graph/prompts/kg_prompts.py` | **大段字符串常量** + `PROMPT_MAPPING` | 图谱子图：护栏、规划、工具选择、Cypher 生成/审计、汇总、终答；供多节点 `ChatPromptTemplate` 引用。 |
| `gustobot/application/agents/kg_sub_graph/agentic_rag_agents/components/*/prompts.py` | **`create_*_prompt_template()` 工厂** | 把 `kg_prompts` 或本地文案包成 `ChatPromptTemplate`（system + human 槽位）；如 `guardrails`、`planner`、`tool_selection`、`summarize`、`text2cypher/*`、`text2sql/*`、`validate_final_answer`、`visualize/*`。 |
| `gustobot/application/agents/kg_sub_graph/agentic_rag_agents/components/cypher_tools/prompts.py` | **独立模板** | Text2Cypher 主链上的生成/校验/纠错模板（文风与 `kg_prompts` 中 `TEXT2CYPHER_*` 可并存，**以实际 `node` 引用为准**）。 |
| `gustobot/application/agents/kg_sub_graph/agentic_rag_agents/workflows/multi_agent/multi_tool.py` | **内联 `ChatPromptTemplate.from_messages`** | KB 多工具子图：`guardrails_prompt`、`router_prompt`、`final_prompt`（未抽到独立 `prompts.py`）。 |
| `gustobot/application/prompts/search_prompts.py` | 常量 | 联网搜索：`SEARCH_SYSTEM_PROMPT`、`SEARCH_SUMMARY_PROMPT`（工具描述、日期、引用格式）。 |
| `gustobot/application/services/search_service.py` | 编排 | 消费 `search_prompts`，与工具调用、摘要生成组合（非主图节点，属应用服务层）。 |
| `gustobot/application/agents/kb_tools/prompts.py` | 函数 `build_knowledge_system_prompt` | 基于 Milvus 等检索结果动态拼 **参考文档** 段。 |
| `gustobot/application/agents/kg_sub_graph/prompts/schema_utils.py` | 工具函数 | 将 Neo4j schema 等压成可塞进 Human 消息的文本（**不是**一整段角色提示，而是**提示的输入料**）。 |
| `gustobot/application/agents/kg_sub_graph/kg_tools_list.py` | Pydantic 工具类 | `Field(description=...)` 进入 OpenAI tools schema，与 `TOOL_SELECTION_SYSTEM_PROMPT` **叠加**。 |

**小结**：「**一段话定义角色与规则**」优先放在 `lg_prompts.py` / `kg_prompts.py`；「**system/human 多消息 + 变量槽位**」放在各组件 `prompts.py` 的工厂函数；KB 子图内联在 `multi_tool.py` 是历史折中，修改时建议与第 4 节对照全文搜索字符串。

### 10.3 编排模式（怎么接到模型上）

1. **纯字符串 + `.format()` / f-string**  
   主图部分节点把 `GENERAL_QUERY_SYSTEM_PROMPT.format(logic=...)` 等拼成一条 system message，再与用户消息列表一并 `ainvoke`。

2. **`ChatPromptTemplate.from_messages([("system", ...), ("human", ...)])`**  
   图谱侧普遍模式：`system` 固定为 `*_SYSTEM_PROMPT` 常量，`human` 带 `{question}`、`{context}` 等；链式 `| llm` 或先 `format_messages` 再调用。

3. **结构化输出**  
   `ROUTER_SYSTEM_PROMPT` → `Router`；补充信息护栏 → `AdditionalGuardrailsOutput`；KB 护栏/路由 → `KBGuardrailsDecision` / `KBRouteDecision`。提示词里写的「输出 JSON / 输出 continue」若与 **Pydantic 字段字面** 不一致，会以 **schema 为准**（见第 3.2 节），属于提示词工程里要重点对齐的一类问题。

4. **工具绑定**  
   `tool_selection`：`tool_selection_prompt | llm.bind_tools(tool_schemas) | PydanticToolsParser`；**工具说明**来自 Pydantic 模型的 `Field(description=...)`（`kg_tools_list.py`），与 `TOOL_SELECTION_SYSTEM_PROMPT` **叠加**生效——改选型行为时要两处都考虑。

5. **动态上下文注入**  
   - **图谱**：`retrieve_and_parse_schema_from_prompts`、Few-shot 示例检索结果写入 human 或中间状态。  
   - **RAG**：`{context}`、`build_knowledge_system_prompt(context)`。  
   - **路由**：完整 `state.messages` 进路由模型，支持多轮消歧。

### 10.4 与代码逻辑的「组合拳」

| 机制 | 作用 |
|------|------|
| **L1 启发式 `_heuristic_router`** | LLM 失败或非法 `type` 时关键词兜底；与 `ROUTER_SYSTEM_PROMPT` 长期并存时需同步调整关键词，否则「训练」了模型却忘了兜底。 |
| **`tool_selection` 启发式** | `DESCRIPTIVE_KEYWORDS` → 直跳 GraphRAG；`_looks_like_sql_question` + `route_type == text2sql-query` → 直跳 Text2SQL；**先于** `bind_tools` 链执行。 |
| **`configurable` 覆盖** | `image_path` / `file_path` 强制改道，提示词分类结果可被覆盖（第 2.4 节）。 |
| **`PROMPT_MAPPING`（kg_prompts）** | 按 key 取整段 system 文本，便于脚本或统一配置扩展；当前未覆盖 `TOOL_SELECTION` 等全部 key，**以各 `create_*` 实际引用为准**。 |

### 10.5 命名、重复与一致性风险

- **同名不同义**：`lg_prompts.GUARDRAILS_SYSTEM_PROMPT`（补充信息分支，`proceed`/`end`）与 `kg_prompts.GUARDRAILS_SYSTEM_PROMPT`（图谱子图，`planner`/`end`）**禁止混贴**。  
- **Cypher 双轨**：`kg_prompts.TEXT2CYPHER_*` 与 `cypher_tools/prompts.py` 内模板可能同时存在；升级图谱 Schema 描述时要确认 **执行链到底 import 哪一套**。  
- **占位符**：`lg_prompts.py` 顶部注明花括号名；改 `{logic}`、`{context}` 等必须同步改 `lg_builder` 里的 `format` 参数。  
- **张力**：同一产品里「追问尽量短」与「general 分支长文指导」并存时，属于**故意保留的多目标提示**，收紧口径时建议一次改全相关常量。

### 10.6 温度、模型与 Key

- **主图侧示例**：路由 **`temperature=0.7`**（`tags=["router"]`）；一般问答与补充信息追问 **`0.7`**；**`create_research_plan`** 外层模型 **`0.7`**（`tags=["research_plan"]`）；**`create_kb_query`** 子图 **`0.3`**（`tags=["kb_multi_tool"]`）。  
- 子图内 Text2SQL / Cypher 等节点可在各自 `prompts.py` 或节点构造处另设 **`0`**，排错时**勿假设全图同温**。  
- 未配置 LLM Key 时路由 / KB 多工具等节点直接失败，**不会**落到「无提示词的默认回复」——属于部署与提示词工程的交界。

### 10.7 修改与回归（在原有第 8 节基础上的检查单）

除第 8 节步骤外，建议增加：

1. **结构化字段**：改护栏/路由文案时对照 **Pydantic 模型字段名与 Literal 取值**。  
2. **双源提示**：改 Cypher 规则时搜索 `TEXT2CYPHER` 与 `cypher_tools/prompts` 两处。  
3. **工具描述**：改 `TOOL_SELECTION_SYSTEM_PROMPT` 时扫一眼 `kg_tools_list` 里各工具类的 `Field(description)`。

## 11. 注意事项、排错与自查清单

### 11.0 改提示词前的快速检查清单（初学者向）

在提交或发布前，可按表勾选（与 **§0.5～0.7**、**§8**、**§10.7** 一致）：

| # | 检查项 |
|---|--------|
| 1 | 是否已定位**唯一**权威源文件？是否搜过项目里**是否还有第二份**同类提示（尤其 `GUARDRAILS`、`TEXT2CYPHER`）？ |
| 2 | 若涉及 **Router / 护栏 / KBRoute** 等结构化输出：Pydantic 字段名、Literal 取值是否与文案一致？ |
| 3 | 是否同步了 **`allowed_types`**、`route_query` 映射、**启发式关键词**（若你改变了分类语义）？ |
| 4 | 工具相关是否同时看了 **`TOOL_SELECTION_*`** 与 **`kg_tools_list` 的 `Field(description)`**？ |
| 5 | 是否知道当前节点 **temperature / tags**？流式前端是否依赖 **tags**？ |
| 6 | 是否用**固定问句**做过手工或自动化回归（不必全覆盖，但要有代表例）？ |
| 7 | 文档 **[智能体路由速查.md](智能体路由速查.md)** 中与行为承诺一致的表格是否需更新？ |

### 11.1 部署与密钥

- 路由节点在 **未配置 `OPENAI_API_KEY`** 时 **`RuntimeError` 直接失败**，没有「无 LLM 的降级闲聊」。这与向量库文档中「服务先能起来」不同，属于 **硬依赖**。  
- 子图内节点可能使用 **同一 base_url / 不同 temperature**；排查「为什么 SQL 很稳、路由很飘」时先看 **各节点实例化参数**，不要只怪提示词。
- **`RAGSEARCH_SYSTEM_PROMPT` / `GENERATE_QUERIES_SYSTEM_PROMPT` / `check_hallucinations`**：主 **`graph = builder.compile(...)` 路径未接入**，改它们**不会**影响当前默认对话；若文档或 README 仍写「最终回答用 RAGSEARCH」，以 **实际 `add_node` 列表**为准。

### 11.2 结构化输出与文案对齐

- **`AdditionalGuardrailsOutput`**：`GUARDRAILS_SYSTEM_PROMPT` 正文若仍写 `continue`/`end`，与字段 `proceed`/`end` **字面不一致**，应以 **Pydantic 与 `with_structured_output` 为准**；改提示时建议统一用词，并在小模型上回归。  
- **`Router.type`**：必须是 `lg_states.Router` 里 Literal 集合之一；改 L1 分类时同步改 **`allowed_types`**（`lg_builder.analyze_and_route_query`）与 **`route_query`** 映射，否则会出现「模型输出了新类型但图不接」的静默风险（若未校验会进 fallback）。

### 11.3 启发式与提示词「抢方向盘」

- **合法 LLM 结构化输出不会再过 `_heuristic_router`**；启发式仅在 **异常或非法 type** 时介入。因此：你如果把 `ROUTER_SYSTEM_PROMPT` 调得很激进，但线上大量失败 fallback，用户看到的仍是 **关键词兜底行为**——排错时要 **看日志里是否 Router LLM failed / invalid type**。  
- **图谱 `tool_selection`**：`DESCRIPTIVE_KEYWORDS`、`_looks_like_sql_question` 等 **先于** `bind_tools` 执行；只改 `TOOL_SELECTION_SYSTEM_PROMPT` 可能改变不了已被代码短路的路径。

### 11.4 附件与 configurable

- 存在 **`image_path` / `file_path`** 时 **覆盖 L1 分类**（第 2.4 节）。调试「为什么明明像 graphrag 却进了图片节点」时先查 API 是否带了附件字段。

### 11.5 流式与 tags

- 前端若按 **`tags`** 过滤 chunk（如只显示 `router`），改节点时 **漏打 tag 或复用错 tag** 会导致「界面没字但后端其实在跑」。新增节点建议与现有 tag 命名风格一致。

### 11.6 自查表（建议收藏）

| 现象 | 优先排查 |
|------|----------|
| 整句都进错分支 | `ROUTER_SYSTEM_PROMPT` 与 `Router` Literal；`route_query`；是否有附件覆盖 |
| 仅偶发错分支 | 路由是否失败走启发式；温度；历史过长导致意图漂移 |
| 图谱里总选错工具 | `tool_selection` 启发式 + `kg_tools_list` 的 `Field(description)` + `TOOL_SELECTION_SYSTEM_PROMPT` 三处 |
| KB 子图总说「不讲做法」却仍讲做法 | `multi_tool.py` 里 `final_prompt` 与 `router_prompt` 是否被改冲突 |
| 护栏莫名全拒 | 两处 **不同** `GUARDRAILS` 是否改混；schema 字段是否与提示一致 |
| 改 Cypher 规则不生效 | `kg_prompts.TEXT2CYPHER_*` 与 `cypher_tools/prompts.py` 实际引用链 |
| 改了 RAGSEARCH 但没效果 | 主图未调用该常量；应改 `kb_tools` / KB 子图 `final_prompt` 或自行挂节点 |
| text2sql 总走 Cypher | L1 是否真为 `text2sql-query`；`route_type` 是否传入；`tool_selection` 是否被 `DESCRIPTIVE_KEYWORDS` 抢到 GraphRAG |

## 13. 未来可能的优化方向

以下为演进建议，实施前需结合产品边界、模型能力与测试集评估。

1. **路由上下文治理**：对送入 `analyze_and_route_query` 的 `messages` 做滑动窗口、摘要或「仅最近 N 轮 + 当前问句」，降低成本与意图漂移。  
2. **提示词版本化**：`ROUTER_SYSTEM_PROMPT` 等用大版本号或 Git 标签记录在日志/元数据，便于线上对比 A/B。  
3. **护栏文案与 schema 一键对齐**：生成测试用例或 lint：扫描提示中的 `continue`/`end` 与 Pydantic Literal 是否冲突。  
4. **集中管理 KB 内联提示**：将 `multi_tool.py` 中 `guardrails_prompt` / `router_prompt` / `final_prompt` 抽到独立 `prompts.py` 或 YAML，便于 diff 与翻译。  
5. **工具选择与提示联合调优**：为 `TOOL_SELECTION` 建立固定问题集，自动断言 `tool_calls` 分布。  
6. **多语言**：路由与分支提示目前以中文为主；若接入英文用户，需分层翻译并回归结构化输出字段。  
7. **小模型专用提示**：路由用轻量模型时，缩短 `ROUTER_SYSTEM_PROMPT`、减少矛盾规则，提高遵循率。  
8. **可观测性**：对「路由失败率、非法 type 率、护栏 end 比例、各 tag 首 token 延迟」打点，和提示版本关联。  
9. **与 [优化与演进建议.md](优化与演进建议.md) 对齐**：产品级策略（如做法走 KB 还是图谱）在文档第 9 节已有草案，可升级为实验开关而非直接改死提示。
