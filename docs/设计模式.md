# Agent 项目中的设计模式说明

本文从**软件设计模式**角度归纳 GustoBot 智能体相关代码的常见写法：它们解决什么问题、在仓库里落在哪些目录，以及**初学者**阅读源码时如何建立预期。说明以**实际结构为准**，不等同于「每个文件都严格对应 GoF 某一模式」；多处是**组合使用**。

**相关文档**：[agent项目架构说明.md](agent项目架构说明.md)、[智能体路由速查.md](智能体路由速查.md)、[提示词工程.md](提示词工程.md)、[agent开发项目总览.md](agent开发项目总览.md)。

### 与 ReAct / AgentExecutor 的关系（常被问到）

- **不是**以经典 **ReAct 提示范式**（显式 `Thought` / `Action` / `Observation` 在同一线程里多轮自循环）作为**主架构**；也未把 LangChain **`AgentExecutor`** 那种「单 Agent 反复调工具直到停」的循环当作 HTTP 聊天主入口。  
- **实际是**：**LangGraph `StateGraph`** —— 节点与条件边描述业务流程；「行动」往往是 **跳到子图节点**（如 Cypher / SQL / LightRAG），工具选择处用 **`llm.bind_tools` + `PydanticToolsParser`**，再用 **`Command`/`Send`** 路由到下一节点，而不是 ReAct 论文式的纯文本交替（详见 [agent开发项目总览.md](agent开发项目总览.md) 与 `tool_selection/node.py`）。  
- **前端 README 中的 React**：指 **React.js UI**，与智能体 **ReAct 模式**无关。

---

## 0. 初学者导读：先抓三条主线

1. **分层**：HTTP 在 `interfaces/`，编排与图在 `application/agents/`，连库与向量在 `infrastructure/`——依赖方向大体 **由外向内、内层不依赖 FastAPI**。  
2. **图 = 状态机**：LangGraph 的 `StateGraph` 注册**节点函数**，用**边**和**条件边**表达分支；状态类型多为 **TypedDict / Pydantic**，节点返回 **部分更新**。  
3. **工厂函数**：大量 `create_*_node`、`create_*_workflow` 接收 `llm`、`graph` 等依赖，返回**可调用节点**或 **编译后的子图**，便于测试时注入假实现。

下文按模式分类描述；最后一节给出**对照表**与**注意事项**。

---

## 1. 分层架构（Layered / 六边形思想）

**意图**：把「对外协议」「业务编排」「技术实现」分开，降低修改一处牵一片的风险。

| 层 | 典型目录 | 职责 |
|----|----------|------|
| 接口层 | `gustobot/interfaces/http/` | REST、Pydantic 请求响应、路由注册 |
| 应用层 | `gustobot/application/agents/`、`application/services/`、`application/prompts/` | LangGraph 编排、子图、领域服务、提示词 |
| 领域层 | `gustobot/domain/` | 领域模型（当前较薄，可扩展） |
| 基础设施层 | `gustobot/infrastructure/` | 日志、ORM、Milvus、Embedding、工具实现等 |

**在本项目中的体现**：`knowledge_router` 只依赖 `KnowledgeService` 抽象能力，不直接拼 Milvus SDK；图谱子图通过 `Neo4jGraph` 等与具体存储对话。

---

## 2. 状态图 + 构建器（State Pattern × Builder）

**意图**：用**显式状态类型**表达「图里流动什么数据」，用 **Builder**（`StateGraph` 的 `add_node` / `add_edge` / `add_conditional_edges` / `compile`）**逐步装配**可执行工作流。

**主图**（`lg_builder.py`）：`AgentState` 在节点间传递；`MemorySaver` 作检查点，按 `thread_id` 恢复会话。

```1062:1080:gustobot/application/agents/lg_builder.py
# 主状态图：入口为意图识别，经条件边分发到各业务节点
builder = StateGraph(AgentState, input=InputState)
# 注册节点
# 只传函数一个参数时，LangGraph 会用函数的 __name__ 作为节点名
builder.add_node(analyze_and_route_query)  # 意图识别与路由决策
builder.add_node(respond_to_general_query)  # 一般问答（仅大模型，不调外部工具）
builder.add_node(get_additional_info)  # 补充信息 / 护栏与引导话术
builder.add_node("create_research_plan", create_research_plan)  # 图谱多工具（GraphRAG、Cypher、Text2SQL 等）
builder.add_node(create_image_query)  # 文生图或视觉识别
builder.add_node(create_file_query)  # 文件接入与知识库写入
builder.add_node(create_kb_query)  # 向量知识库多工具工作流


# 边：START → 路由节点 → 条件边按 route_query 结果跳转
builder.add_edge(START, "analyze_and_route_query")
builder.add_conditional_edges("analyze_and_route_query", route_query)

# 编译后的可执行图；与 checkpointer 组合后支持按 thread_id 恢复状态
graph = builder.compile(checkpointer=checkpointer)
```

**子图**：如 `create_multi_tool_workflow`、`create_text2sql_workflow`、`create_text2cypher_agent` 同样 **`StateGraph(...).compile()`**，输入/输出状态类型与子任务对齐（如 `OverallState`、`Text2SQLState`）。

**初学者注意**：节点函数一般返回 **`dict` 片段**合并进状态，而不是整图重算；读代码时先看 **状态类型定义**（`lg_states.py`、`components/state.py` 等）。

---

## 3. 策略模式（Strategy）与条件路由

**意图**：把「下一步走哪条分支」从业务节点中抽出，由**路由函数**或 **LLM 结构化输出**决定，便于增删分支而不改无关节点。

**典型位置**：

- **L1 主路由**：`route_query(state)` 根据 `Router.type` 返回下一节点名；`analyze_and_route_query` 用 **`with_structured_output(Router)`** 得到分类结果。  
- **L2 工具选择**：`tool_selection` 结合 **规则捷径**（如 `_looks_like_sql_question`）与 **`bind_tools` + `PydanticToolsParser`**，等价于多策略择优。  
- **Text2SQL**：`validate_sql` 后 **`add_conditional_edges`**，` _should_execute_or_retry` 在「执行 / 重试生成 / 结束」间切换。

这与经典 Strategy 的共同点：**算法（分支选择）可替换**；差异是部分「策略」写在**提示词 + 结构化 schema**里，部分写在**纯代码关键词**里。

---

## 4. 工厂方法与依赖注入（Factory + DI）

**意图**：节点创建时集中处理依赖（LLM、图、检索器），调用方只拿「可运行的闭包」。

**工厂函数**（节选命名习惯）：

- `create_knowledge_query_node(knowledge_service=..., llm_client=...)`  
- `create_text2cypher_generation_node(llm, graph, cypher_example_retriever)`  
- `create_multi_tool_workflow(...)` → `CompiledStateGraph`  
- `create_kb_multi_tool_workflow(...)`  

**依赖注入**：

- **构造参数**：工厂接收 `llm`、`Neo4jGraph` 等，测试可传入 mock。  
- **FastAPI**：`Depends(get_knowledge_service)` 在请求作用域注入服务（向量路由）。  
- **LangGraph `config.configurable`**：`thread_id`、`image_path`、`file_path` 等运行时配置，相当于**上下文注入**。

---

## 5. 外观模式（Facade）

**意图**：对外暴露简单 API，屏蔽子系统组合细节。

**典型**：`KnowledgeService` 封装 **切块、Embedding、Milvus、Rerank**；图谱侧一次 `create_research_plan` 内组装 **multi_tool_workflow** 并 `ainvoke`，对主图而言就是一个节点。

---

## 6. 适配器模式（Adapter）

**意图**：对接第三方协议，使上层代码保持稳定接口。

**典型**：

- **`OpenAICompatibleEmbeddings`**：用 OpenAI 兼容 HTTP 对接不同厂商 Embedding。  
- **`Reranker`**：`provider` 为 `custom` / `cohere` / `jina` / `voyage` 等时分支调用，对上统一 `rerank(query, documents, top_k)`。  
- **LangChain `ChatOpenAI` + `openai_api_base`**：统一聊天补全入口。

---

## 7. 模板方法 / 管道（Template Method × Pipeline）

**意图**：固定「先提示、再模型、再解析」的骨架，子步骤通过换 **prompt 模板**或 **Parser** 变化。

**典型**：`ChatPromptTemplate | llm | StrOutputParser`、`prompt | llm.bind_tools(...) | PydanticToolsParser`；Text2Cypher 链上 **generate → validate → (correct) → execute** 即流水线阶段。

---

## 8. 命令模式（Command）与节点闭包

**意图**：把「一步操作」封装成**可调用对象**（异步函数），由图调度器在适当时机执行，而不在注册时立刻运行。

LangGraph 的 **node** 多为 `async def xxx(state) -> dict`，符合「命令 = 可执行单元」；**Map-Reduce / Send**（若使用）则像批量派发命令，见 `multi_agent/edges.py` 等。

---

## 9. 单例与服务定位器（Singleton / Service Locator，轻量）

**意图**：昂贵或需全局一致的资源只初始化一次。

**典型**：

- `get_lightrag_service()`：LightRAG 服务单例。  
- `knowledge_router` 中 `@lru_cache` 的 `get_neo4j_qa_service()`。  
- 模块级 **`graph = builder.compile(...)`**：主图单实例供 API 引用。

**注意**：`get_knowledge_service()` **每请求 new**（向量路由）与上述不同，属于**有意的短生命周期**或历史折中，见 [向量知识库.md](向量知识库.md) 注意事项。

---

## 10. 原型 / 备忘录（Memento）：检查点

**`MemorySaver` + `thread_id`** 保存对话状态，支持多轮与中断恢复（进程内、重启丢失）。更接近 **备忘录**（保存并恢复状态快照），而非深拷贝 **原型**。

---

## 11. 类型对象与值对象：Pydantic / Literal

**意图**：路由结果、护栏决策、工具参数用 **Pydantic 模型** + **`Literal`** 限定取值，与 **`with_structured_output`** 配合，减少自由文本解析。

**副作用**：提示词里的字面量（如 `continue` vs `proceed`）若与 schema 不一致，会产生工程隐患，见 [提示词工程.md](提示词工程.md)。

---

## 12. 代理 / 组合：子图当作「大节点」

主图节点 **`create_research_plan`**、**`create_kb_query`** 内部 **`await subgraph.ainvoke(...)`**，对外表现为一个节点，内部是完整子图。这是 **组合优于继承** + **子图封装**。

---

## 13. 再导出与 DRY（非经典模式，但属工程约定）

`application/agents/text2sql/components/*` **再导出** `agentic_rag_agents/components/text2sql` 的节点工厂，避免两套 Text2SQL 实现分叉。阅读时以 **实际 import 链**为准。

## 14. 模式对照简表（快速查阅）

| 模式/思想 | 本项目中的主要落点 |
|-----------|-------------------|
| 分层 | `interfaces` / `application` / `infrastructure` / `domain` |
| Builder | `StateGraph` 装配 + `compile()` |
| State | `AgentState`、`OverallState`、`Text2SQLState` 等 |
| Strategy | `route_query`、条件边、工具选择、启发式关键词 |
| Factory | `create_*_node`、`create_*_workflow` |
| Facade | `KnowledgeService`、`create_research_plan` 对子图 |
| Adapter | 兼容 Embedding、Rerank 多厂商、OpenAI 兼容基址 |
| Pipeline | `prompt \| llm \| parser`、Text2Cypher / Text2SQL 链 |
| 编排范式（非 GoF） | **LangGraph 工作流** 为主；**非**经典 ReAct 文本循环、**非** AgentExecutor 主入口 |
| Command | 异步节点函数由图调度 |
| Singleton / 模块单例 | `graph`、`get_lightrag_service`、`lru_cache` QA |
| Memento | `MemorySaver` + `thread_id` |

## 15. 注意事项（改代码前必读）

1. **改路由 = 改图 + 改类型 + 改提示**：新增 `Router.type` 时同步 **`allowed_types`**、`route_query`、提示词与文档。  
2. **条件边与死循环**：Text2SQL 等重试边要有 **上限** 或 **终止条件**，避免无限 `retry`。  
3. **子图输入输出契约**：`create_research_plan` 传入的 `input_state` 键名必须与子图 **`input=`** 类型一致。  
4. **测试**：工厂注入使节点可单测；全图集成测需 mock LLM 或用小模型。  
5. **不要把业务规则只写在提示里**：关键安全路径（如 SQL 执行前）应有 **代码层校验**（validators），与提示词双保险。

---

## 16. 未来可演进方向（与模式相关）

1. **显式端口接口**：为 `KnowledgeService`、`Retriever` 定义 Protocol/ABC，便于换实现与单测。  
2. **路由策略插件化**：L1/L2 注册表配置化，减少改核心 `lg_builder`。  
3. **检查点持久化**：从 `MemorySaver` 扩展到 Redis/DB，满足多实例与重启续聊。  
4. **图版本与灰度**：主图/子图 `compile` 结果带版本号，便于 A/B。  

更偏产品与技术路线的列表见 [优化与演进建议.md](优化与演进建议.md)。
